 ============================================================
 CLAUDE FUNDAMENTALS
============================================================
GOAL:
Understand how Claude processes a software-development task
before learning advanced Claude Code features.

The goal is NOT to learn random prompts.

The goal is to learn how to give Claude:
    Context
    Instructions
    Constraints
    Goals
    Verification steps
------------------------------------------------------------
1. WHAT CLAUDE CAN / CANNOT SEE
------------------------------------------------------------
Claude can only work with information that is available to it
through its current conversation, project context, files,
tools, or integrations.

For software development, Claude may be able to inspect:

- Project files
- Source code
- Configuration files
- Git repository
- Terminal output
- Error messages
- Tests
- Documentation
- Tool results

Claude does NOT automatically know everything about your
application or business.

Example:
BAD:

    "Fix authentication."

Claude does not know:
- What authentication system you use
- Where authentication is implemented
- What the bug is
- What the expected behavior is

BETTER:
    "Inspect the authentication implementation.

    First inspect:
    - auth module
    - JWT guard
    - GraphQL context
    - user service
    - login resolver

    Do not modify anything yet.
    Explain the current authentication flow."

IMPORTANT:
Never assume Claude understands your entire project.

First allow Claude to inspect the relevant context.
------------------------------------------------------------
2. CONTEXT WINDOW
------------------------------------------------------------
A context window is the amount of information Claude can
consider during a conversation/task/session.

Think of it as Claude's current working memory.

Example:

    User message
          +
    Project instructions
          +
    Files Claude reads
          +
    Tool results
          +
    Previous conversation
          =
       CONTEXT

If the context becomes very large, Claude may have less
effective access to earlier details.

Therefore:
    More context != always better context

The goal is:
    RELEVANT CONTEXT

not:
    ALL POSSIBLE CONTEXT

so if topic change create new session
------------------------------------------------------------
3. TOKENS
------------------------------------------------------------
Tokens are the units used to process text.

For example:
    "authentication"

may be represented internally as one or more tokens.
Code also consumes tokens.
A large project can therefore create a very large context.

You should understand:

    More files
        ↓
    More text
        ↓
    More tokens
        ↓
    Larger context

Therefore, don't unnecessarily give Claude thousands of
irrelevant files.

Instead:

    Task
      ↓
    Identify relevant files
      ↓
    Read relevant files
      ↓
    Work on task
------------------------------------------------------------
4. CONTEXT ACCUMULATION
------------------------------------------------------------
During a long Claude session, information can accumulate.

Example:

    User request
        ↓
    Claude reads auth
        ↓
    Claude reads user module
        ↓
    Claude modifies login
        ↓
    Claude runs tests
        ↓
    Claude fixes error
        ↓
    Claude modifies another file

The conversation now contains a lot of information.

This can be useful because Claude remembers the work being
done in the current context.

But it can also become noisy.

Therefore learn when to:
    Continue the current conversation

and when to:
    Start a fresh context

Important principle:

    Long conversation
        ≠
    Automatically better conversation
------------------------------------------------------------
5. INSTRUCTIONS VS CONTEXT
------------------------------------------------------------
These are different things.
CONTEXT:
Information Claude needs to understand the problem.

Example:
    "The application uses NestJS, GraphQL, MySQL and Redis."

INSTRUCTION:
What you want Claude to do.

Example:
    "Inspect the authentication flow."

CONSTRAINT:
What Claude must NOT or MUST do.

Example:
    "Do not modify the database schema."

GOAL:
What the final result should achieve.

Example:
    "Fix the authentication bug without changing
     the existing GraphQL API."

A good software task contains all four:

    CONTEXT
       +
    INSTRUCTION
       +
    CONSTRAINTS
       +
    GOAL

------------------------------------------------------------
6. SYSTEM INSTRUCTIONS
------------------------------------------------------------
System instructions are high-level instructions that control
how Claude should behave.

As a user, you normally don't control the underlying system
instructions.

You should understand the concept:

    System instructions
          ↓
    Developer/project instructions
          ↓
    User instructions
          ↓
    Context/files/tools

The important lesson is:
Claude follows a hierarchy of instructions.

Therefore, don't assume that writing:
    "Ignore all previous instructions."

will necessarily override higher-priority instructions.

For your development work, focus mainly on:

    Project instructions
    User instructions
    Task constraints
------------------------------------------------------------
7. PROJECT INSTRUCTIONS
------------------------------------------------------------
Project instructions define how Claude should work inside
your project.

A common example is:
    CLAUDE.md

Think of this as:
    PROJECT ENGINEERING RULEBOOK

Example:
    Project:
    NestJS + GraphQL + TypeORM + MySQL

    Rules:
    - Use TypeScript strict mode
    - Do not use any
    - Follow existing architecture
    - Do not introduce unnecessary dependencies
    - Validate GraphQL inputs
    - Never expose secrets
    - Do not modify database schema without approval
    - Write tests for business logic
    - Run tests after implementation
    - Review git diff before finishing

Now Claude doesn't need you to repeat these rules
every time.
------------------------------------------------------------
8. PROMPT STRUCTURE
------------------------------------------------------------

A strong software-development prompt can follow this
structure:

    CONTEXT
       ↓
    TASK
       ↓
    CONSTRAINTS
       ↓
    PROCESS
       ↓
    EXPECTED RESULT
       ↓
    VERIFICATION


Example:

    CONTEXT:
    This is a NestJS + GraphQL application.
    Authentication uses JWT and Redis.


    TASK:
    Investigate why authenticated GraphQL requests are
    sometimes returning Unauthorized.


    CONSTRAINTS:
    - Do not change the JWT strategy yet.
    - Do not modify the database.
    - Do not install new packages.


    PROCESS:

    1. Inspect the authentication module.
    2. Inspect JWT guard.
    3. Inspect GraphQL context.
    4. Trace how the request reaches the resolver.
    5. Identify the root cause.


    EXPECTED RESULT:

    Explain:
    - current authentication flow
    - root cause
    - recommended fix
    - files that need modification


    VERIFICATION:
    Do not modify code until the root cause is confirmed.
------------------------------------------------------------
9. GIVE CLAUDE CONSTRAINTS
------------------------------------------------------------
Constraints are extremely important in production.

Without constraints:
    Claude may solve the problem
    but change things you didn't want changed.

Example:
    "Fix the login bug."

Better:
    "Fix the login bug.

    Constraints:
    - Do not change the API response.
    - Do not change the database schema.
    - Do not change JWT expiration.
    - Do not add dependencies.
    - Follow the existing architecture."


Another example:
    "Refactor this service.

    Constraints:
    - Preserve public method signatures.
    - Preserve database behavior.
    - Preserve GraphQL API.
    - Do not change unrelated files."


IMPORTANT:
The more dangerous the task,
the more explicit your constraints should be.
------------------------------------------------------------
10. ASK CLAUDE TO INSPECT BEFORE MODIFYING
------------------------------------------------------------
This is one of the most important habits.

DO NOT immediately say:
    "Implement this feature."

Instead:
    "First inspect the existing implementation.

    Do not modify anything.

    Explain:
    1. Current architecture
    2. Relevant files
    3. Existing behavior
    4. Problems
    5. Proposed implementation

    Wait before making changes."


Why?

Because Claude may otherwise make assumptions.

Production workflow:

    INSPECT
       ↓
    UNDERSTAND
       ↓
    PLAN
       ↓
    APPROVE
       ↓
    IMPLEMENT
------------------------------------------------------------
11. ASK CLAUDE TO EXPLAIN BEFORE CODING
------------------------------------------------------------
For important features, separate:
    THINKING / DESIGN

from:
    IMPLEMENTATION

Example:
    "I need to add refresh-token authentication.

    First do not write code.

    Analyze:
    - current authentication architecture
    - token storage
    - Redis usage
    - GraphQL context
    - cookie handling
    - security considerations

    Then propose an implementation plan.
    Wait for my approval."

This gives you a chance to catch bad architecture BEFORE
Claude writes many files.
------------------------------------------------------------
12. ASK CLAUDE TO VERIFY ITS CHANGES
------------------------------------------------------------
Never assume:

    Code generated
        =
    Code correct

After implementation:

    Run tests
    Check TypeScript
    Check lint
    Inspect git diff
    Check edge cases
    Review security
    Verify expected behavior

Example:

    "Now verify your implementation.

    1. Run the relevant tests.
    2. Check TypeScript errors.
    3. Check lint errors.
    4. Inspect the git diff.
    5. Look for unintended changes.
    6. Check edge cases.
    7. Explain anything that failed.

    Do not claim success unless you actually verified it."

This is one of the biggest differences between:
    BEGINNER CLAUDE USER

and:
    PROFESSIONAL CLAUDE USER
