# 📘 System Design Notes
## 🎯 Why Do We Need to Learn System Design?

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🤔 What is System Design?

System Design is the process of designing an application so that it can handle
millions of users efficiently, reliably, and securely.

It answers questions like:
• How should users connect to the server?
• How should data be stored?
• How can the system handle millions of requests?
• What happens if one server crashes?
• How can we make the application fast?

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

❓ Why Can't We Use Just One Server?

Imagine you build an Instagram clone.

Initially:

👤 Users: 100
🖥 Server: 1
💾 Database: 1

Everything works perfectly.

Now imagine:

👤 Users: 10 Million
📸 Photos: 500 Million
❤️ Likes every second: 50,000
💬 Messages every second: 100,000

One server cannot handle this much traffic.

The application becomes:
❌ Slow
❌ Crashes
❌ Times Out
❌ Loses users

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 Purpose of System Design

System Design teaches us how to build applications that are:

✅ Fast
✅ Scalable
✅ Reliable
✅ Highly Available
✅ Secure
✅ Easy to Maintain

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 What Problems Does System Design Solve?

✅ Server Crash
→ Use Multiple Servers

✅ Slow Response
→ Use Cache (Redis)

✅ Too Many Users
→ Horizontal Scaling

✅ Huge Database
→ Sharding & Replication

✅ Global Users
→ CDN

✅ Heavy Background Work
→ Message Queue (Kafka/RabbitMQ)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Suppose 20 Million users open YouTube at 8 PM.

❌ Server crashes.

With System Design:
✅ Load Balancer distributes traffic.
✅ Multiple servers handle requests.
✅ Cache serves popular videos quickly.
✅ CDN delivers videos from nearby locations.

Users experience a smooth application.

📚 Difference Between DSA and System Design

DSA
✔ Solves one programming problem efficiently.
✔ Focuses on algorithms and data structures.

System Design
✔ Builds an entire application.
✔ Focuses on architecture, scalability, reliability, and performance.

Example:

DSA:
Find the shortest path in a graph.

System Design:
Design Google Maps.

The app wants to connect to:

💡 DNS is called the Internet's Phonebook.

## 🌐 How Browser, DNS & Express Work Together

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 Example

Frontend Code:

fetch("https://api.myapp.com/users")

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🚀 Complete Flow

1️⃣ React/Frontend calls API

        │
        ▼

2️⃣ Browser checks DNS Cache

        │
        ▼

3️⃣ If IP is NOT found,
    Browser asks DNS Server

api.myapp.com
        │
        ▼
104.20.35.120

📌 DNS converts Domain Name ➜ IP Address

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4️⃣ Browser creates a connection

Connection is made to:

104.20.35.120:443

💡 Computers communicate using IP addresses, NOT domain names.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

5️⃣ Browser sends HTTP Request

Example:

GET /users HTTP/1.1
Host: api.myapp.com

⚠️ Important:

Although the connection is made using the IP address,
the browser STILL sends the original domain name
inside the "Host" header.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

6️⃣ Express Server receives the request

Example:

app.get("/users",(req,res)=>{
    console.log(req.headers.host);
    console.log(req.ip);
})

Express understands the HTTP Request.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

📖 What Express Can Read
✅ req.headers.host

Returns:

api.myapp.com
Meaning:
➡️ Which domain the client requested.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ req.ip

Returns:

203.0.113.5

Meaning:
➡️ Client/User IP Address
(Not the server's IP)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 Important Difference

🌍 DNS
✔ Converts Domain Name ➜ IP Address

🌐 Browser
✔ Creates connection using IP Address

📨 Browser
✔ Sends HTTP Request
✔ Includes Domain Name in Host Header

🖥 Express
✔ Reads HTTP Request
✔ Can access:
   • Domain Name (req.headers.host)
   • Client IP (req.ip)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

❌ Common Misconception

Wrong ❌
Express converts domain name to IP.

Correct ✅
Browser performs DNS lookup BEFORE contacting Express.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

⭐ Interview Points

Q. Who converts Domain Name into IP Address?
✅ DNS (used by Browser/Operating System)

Q. Who establishes the network connection?
✅ Browser/Operating System

Q. Does Express know the server IP?
❌ No. The Operating System has already accepted the connection.

Q. What does Express understand?
✅ HTTP Requests

Q. How does Express know which domain was requested?
✅ From req.headers.host

Q. How does Express know the client's IP?
✅ From req.ip

👉 DNS converts Domain ➜ IP.
👉 Browser connects using the IP.
👉 Browser sends an HTTP request (including the Host header).
👉 Express receives and processes the HTTP request.

        │
        ▼

        │
        ▼
3. DNS returns the IP address
        │
        ▼
4. Browser establishes a TCP connection with that IP
        │
        ▼
5. If HTTPS, TLS/SSL handshake happens
        │
        ▼
6. Browser sends the HTTP request
        │
        ▼
7. Express receives req and res
        │
        ▼
8. Controller executes
        │
        ▼
9. Response goes back to the browser


-----># 📘 Topic: Recursive Resolver (DNS Resolver)

📌 Definition

A Recursive Resolver is a DNS server that finds the IP address for a domain name on behalf of the client (browser or mobile app).
Recursive Resolver = DNS server that finds and caches the IP address for the client.
Think of it as a "middleman" between your browser and the entire DNS system.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

⚡ Why is it Needed?

The browser does NOT know where every website's IP address is.

Instead of searching the whole internet itself, it asks the Recursive Resolver.

Browser
   │
   ▼
Recursive Resolver
   │
   ▼
Finds the IP Address
   │
   ▼
Returns IP to Browser

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🛠 How It Works

Suppose you open:

https://www.google.com

Step 1:
Browser asks:

"What is the IP of www.google.com?"

        │
        ▼

Recursive Resolver

Step 2:
If the IP is already cached,

✅ Returns it immediately.

OR

Step 3:
If not cached,

It asks other DNS servers
(Root → TLD → Authoritative DNS)

Step 4:

Gets the IP

142.250.xxx.xxx

Step 5:

Stores it in cache

Step 6:

Returns IP to Browser

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

📦 Cache Advantage

First User

Browser
   │
   ▼
Recursive Resolver
   │
   ▼
Google DNS Servers

(2-5 ms extra)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Second User

Browser
   │
   ▼
Recursive Resolver

(Cache Hit ✅)

Returns IP immediately

No need to contact other DNS servers.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 Real-Life Example

You ask your teacher:

"Where is Room 305?"

Teacher already knows.

Teacher tells you immediately.

You don't search the entire school.

Recursive Resolver = Teacher

# 📘 Topic: Load Balancer

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

📌 Definition

A Load Balancer is a server (or software) that distributes incoming user requests
across multiple servers so that no single server becomes overloaded.

Think of it as a Traffic Police for servers.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

⚡ Why is it Needed?

Imagine your application has only one server.

               1,00,000 Users
                      │
                      ▼
                 🖥 Server

Problems:

❌ Server becomes slow
❌ High CPU usage
❌ Crashes
❌ Website goes down

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ Solution: Load Balancer

             1,00,000 Users
                    │
                    ▼
             ⚖ Load Balancer
             ┌────┼────┐
             ▼    ▼    ▼
         🖥 S1 🖥 S2 🖥 S3

The Load Balancer receives all requests and distributes them among multiple servers.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🛠 How It Works

Step 1:
Users send requests.

        │
        ▼

Step 2:
Load Balancer receives all requests.

        │
        ▼

Step 3:
It decides which server should handle each request.

Example:

User 1 → Server 1

User 2 → Server 2

User 3 → Server 3

User 4 → Server 1

User 5 → Server 2

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 Real-Life Example

Imagine three billing counters in a supermarket.

Without Load Balancer

Customer
   │
   ▼
Counter 1

Counter 2 and 3 are empty.

Counter 1 becomes overcrowded.

With Load Balancer

Customer 1 → Counter 1

Customer 2 → Counter 2

Customer 3 → Counter 3

Everyone gets served quickly.

Load Balancer = Store Manager directing customers.

⭐ Common Load Balancing Algorithms

1️⃣ Round Robin

Requests are sent one by one.

Request 1 → S1

Request 2 → S2

Request 3 → S3

Request 4 → S1

Request 5 → S2

Simple and most common.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

2️⃣ Least Connections

The request goes to the server with the fewest active users.

Example:

Server 1 → 100 users

Server 2 → 20 users ✅

Server 3 → 80 users

Next request → Server 2

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

3️⃣ IP Hash

Same user's IP always goes to the same server.

Useful for:

✅ Chat Applications
✅ Banking
✅ Shopping Cart

SSL Certificate –
Definition

An SSL Certificate is a digital certificate that verifies a website's identity and 
enables HTTPS by encrypting communication between the client and the server.
SSL (Secure Sockets Layer) is now obsolete. Modern websites actually use TLS (Transport Layer Security),
 but people still commonly say "SSL certificate."

Why SSL is Needed

Without SSL (HTTP):

Data is sent in plain text.
Hackers can read usernames, passwords, and card details.
Vulnerable to Man-in-the-Middle (MITM) attacks.

With SSL (HTTPS):

Data is encrypted.
Only the client and server can read it.
The website's identity is verified.

| HTTP              | HTTPS                  |
| ----------------- | ---------------------- |
| Not secure        | Secure                 |
| No encryption     | Encrypted              |
| Port 80           | Port 443               |
| `http://`         | `https://`             |
| Easy to intercept | Difficult to intercept |

How SSL Works
1. User opens https://example.com
            |
2. Server sends SSL Certificate
            |
3. Browser verifies certificate
            |
4. TLS Handshake
            |
5. Session Key Generated
            |
6. Encrypted Communication Starts

SSL Handshake (Simplified)
Client requests HTTPS connection.
Server sends its SSL certificate.
Browser verifies the certificate.
Client and server agree on encryption algorithms.
They generate a shared session key.
All further communication uses this symmetric session key.


What Does an SSL Certificate Contain?
Domain name
Public key
Certificate Authority (CA)
Expiry date
Digital signature
Organization details (for some certificate types)


Public Key & Private Key
Server
 ├── Public Key  → Shared with everyone
 └── Private Key → Secret, never shared
Public Key: Encrypts data or verifies signatures.
Private Key: Decrypts data or creates digital signatures.

A Certificate Authority (CA) is a trusted organization that issues and signs SSL certificates.

Caching in System Design
Caching is the process of storing frequently accessed data in fast memory so future requests 
can be served quickly without repeatedly querying the database or another slow source.

Goal: Reduce response time, decrease database load, and improve scalability.

Why Caching?

Without Cache

User
  |
App Server
  |
Database

Every request hits the database.

Problems:

High latency
Database overload
Poor scalability

With Cache

User
  |
App Server
  |
Cache (Redis)
  |
Database

Frequently requested data comes from the cache instead of the database.

How Caching Works
1. User requests data
        |
2. Check Cache
        |
   Cache Hit?
   /        \
 Yes         No
 |            |
Return     Query DB
Data          |
              |
         Store in Cache
              |
         Return Data

Cache Hit
Definition: Requested data is found in the cache.

Fast response
Database is not accessed

Cache Miss
Definition: Requested data is not in the cache.

Read from the database
Store data in cache
Return data to the user
Cache Eviction

When the cache is full, some data must be removed.

LRU (Least Recently Used)
Removes the least recently accessed item.
Most common policy.
LFU (Least Frequently Used)
Removes the item accessed the fewest times.
FIFO (First In, First Out)
Removes the oldest cached item.

TTL (Time To Live)
TTL specifies how long data stays in the cache.

Example:

User Profile
TTL = 10 minutes

After 10 minutes, the entry expires and is fetched from the database again.

Types of Cache
1. Browser Cache
Stores static files (images, CSS, JS) in the user's browser.

2. CDN Cache
Stores content on edge servers close to users.

3. Application Cache
Stores frequently used data in memory (e.g., Redis, Memcached).

4. Database Cache
Caches database query results.

Cache-Aside Pattern (Lazy Loading)

Most commonly used.

Database Partitioning (Same Database)
Definition
Database Partitioning is the process of dividing a single large table into smaller partitions within the same database instance.

Goal: Improve query performance, simplify maintenance, and manage very large tables.

One Database
One Table
Multiple Partitions

Without Partitioning
Customer Table

----------------------------------------
ID | Name | City | Date | ...
----------------------------------------
1
2
3
...
100000000

To find one record, the database may need to scan a huge table.

With Partitioning
Customer Table

-------------------------------
Partition 1 (2024)
-------------------------------

-------------------------------
Partition 2 (2025)
-------------------------------

-------------------------------
Partition 3 (2026)
-------------------------------

The database searches only the relevant partition instead of the entire table.

Types of Partitioning
1. Range Partitioning

Rows are divided based on a range of values.
Example:

Orders

2024 Orders → Partition 1

2025 Orders → Partition 2

2026 Orders → Partition 3

Used for:

Date
Salary
Age
Order ID

sql:
CREATE TABLE Orders (
    OrderID INT,
    CustomerID INT,
    OrderDate DATE,
    Amount DECIMAL(10,2)
)
PARTITION BY RANGE (YEAR(OrderDate)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p2026 VALUES LESS THAN (2027),
    PARTITION pFuture VALUES LESS THAN MAXVALUE
);


2. List Partitioning
Rows are divided based on specific values.



Example:

India Users → Partition 1

USA Users → Partition 2

UK Users → Partition 3
sql:
CREATE TABLE Customers (
    ID INT,
    Name VARCHAR(100),
    Country VARCHAR(20)
)
PARTITION BY LIST COLUMNS (Country) (
    PARTITION India VALUES IN ('India'),
    PARTITION USA VALUES IN ('USA'),
    PARTITION UK VALUES IN ('UK')
);


If you insert:

INSERT INTO Customers VALUES
(1, 'Naeem', 'India'),
(2, 'John', 'USA');

The data is stored as:

India Partition
---------------
1 | Naeem | India

USA Partition
-------------
2 | John | USA

UK Partition
------------
Empty


3. Hash Partitioning
Database calculates a hash value.

Partition = UserID % 4

0 → P1

1 → P2

2 → P3

3 → P4

Provides more even data distribution.

4. Key Partitioning

Similar to hash partitioning, but the database chooses the hashing function automatically.

Architecture
Application
      |
      ▼
Database
      |
-----------------------------
|     |      |      |
P1    P2     P3     P4

Everything is inside one database.

Advantages
Faster queries
Smaller indexes
Easier backups
Faster deletes (drop an old partition instead of deleting millions of rows)
Better maintenance

Disadvantages
More complex schema design
Poor partition key selection can hurt performance
Some queries may still scan multiple partitions


| Database Partitioning      | Sharding                                 |
| -------------------------- | ---------------------------------------- |
| Same database              | Multiple databases/servers               |
| Improves query performance | Improves scalability                     |
| Managed by the DBMS        | Managed by the application or middleware |
| One database instance      | Many database instances                  |
|vertical partitioning       | Horizontal partitioning                  |

Real Example

Suppose your Orders table stores data for 10 years.

Without partitioning:

Orders
2020
2021
2022
2023
2024
2025
2026

Query:

SELECT * FROM Orders
WHERE OrderDate BETWEEN '2026-01-01' AND '2026-12-31';

Without partitioning:

Scans the entire table.

With range partitioning by year:

Only the 2026 partition is scanned (called partition pruning), making the query much faster.
Interview Definition

Database partitioning is the technique of dividing a large table into smaller logical partitions within the same database instance,
 allowing the database to scan only relevant partitions, which improves query performance and simplifies maintenance.

CAP Theorem – Short Notes
Definition

CAP Theorem states that a distributed system can guarantee only two out of the following three properties at the same time:

C – Consistency
A – Availability
P – Partition Tolerance

Rule: In the presence of a network partition, you must choose between Consistency and Availability.

The Three Properties
1. Consistency (C)
Every client sees the same, latest data after a write.

Example
User A updates balance = ₹1000

↓

User B immediately reads balance

↓

Gets ₹1000 ✅

All users see the latest value.

2. Availability (A)

Every request receives a response, even if some servers have failed.

Example
Server 1 ❌

↓

Server 2 responds ✅

The system always returns a response, but it may not be the latest data.

3. Partition Tolerance (P)

The system continues working even if communication between servers is interrupted.

Example
Server A  ❌ Network Failure ❌  Server B

Users can still access each server.

The network is split into partitions, but the system keeps operating.

CAP Triangle
          Consistency
               ▲
              / \
             /   \
            /     \
           /       \
Availability-------Partition Tolerance

You can guarantee only two at the same time during a network partition.

CP System (Consistency + Partition Tolerance)
Network Failure

↓

Reject some requests

↓

Always return correct data

Characteristics
Latest data is always returned.
Some requests may fail or wait.

Examples
MongoDB (configured for strong consistency)
Apache HBase
ZooKeeper


AP System (Availability + Partition Tolerance)
Network Failure

↓

Always respond

↓

Data may be stale

Characteristics
Always available.
Different users may temporarily see different values.

Examples
Cassandra
DynamoDB (eventual consistency mode)
Riak

CA System (Consistency + Availability)
Single Database

↓

No Network Partition

↓

Latest Data + Always Available

Characteristics
Works only when there is no network partition.
Not practical for distributed systems because network failures are always possible.
Examples
Traditional single-server SQL databases (before distribution)
Why Can't We Have All Three?

Suppose two database servers lose network connectivity.

Server A   ❌ Network ❌   Server B

A user writes data to Server A.

A user reads from Server B.

Now you have two choices:

Choose Consistency (CP)
Server B refuses request

↓

Correct data maintained

Choose Availability (AP)
Server B returns old data

↓

Always available

You cannot both:

return the latest data (Consistency), and
always return a response (Availability),
while also tolerating the network partition.

| Property                    | Meaning                                |
| --------------------------- | -------------------------------------- |
| **Consistency (C)**         | Every read gets the latest data.       |
| **Availability (A)**        | Every request gets a response.         |
| **Partition Tolerance (P)** | System works despite network failures. |

Interview Questions
What is CAP Theorem?

A distributed system can guarantee at most two of Consistency, Availability, and Partition Tolerance during a network partition.

What is the difference between CP and AP?
| CP                        | AP                    |
| ------------------------- | --------------------- |
| Correct data              | Always responds       |
| May reject/delay requests | May return stale data |

Why is Partition Tolerance important?
Because network failures are inevitable in distributed systems, most real-world distributed systems must tolerate partitions.

One-Line Definition

CAP Theorem states that during a network partition, a distributed system can provide either Consistency or Availability,
 but not both simultaneously, while maintaining Partition Tolerance.

Write-Through vs Write-Back Cache – Short Notes
Write-Through Cache
Definition

In Write-Through, data is written to the cache and the database at the same time.

Flow
Client
   |
Write Request
   |
Cache
   |
Database

How it Works
Client sends a write request.
Cache is updated.
Database is updated immediately.
Success response is returned.

Advantages
Data is always consistent.
No data loss if the cache crashes.
Database always has the latest data.

Disadvantages
Slower writes.
Every write hits both cache and database.


Write-Back (Write-Behind) Cache
Definition

In Write-Back, data is written only to the cache first. The cache updates the database later (asynchronously).

Flow
Client
   |
Write Request
   |
Cache
   |
Return Success
   |
(Background Process)
   |
Database
How it Works
Client sends a write request.
Cache is updated.
Response is returned immediately.
Cache writes to the database later.

Advantages
Very fast writes.
Reduces database load.
Better performance for high write traffic.
Disadvantages
Risk of data loss if the cache fails before syncing.
More complex implementation.        

| Write-Through                  | Write-Back                             |
| ------------------------------ | -------------------------------------- |
| Cache + DB updated immediately | Cache updated first, DB later          |
| Synchronous write              | Asynchronous write                     |
| Slower                         | Faster                                 |
| Strong consistency             | Eventual consistency                   |
| Low risk of data loss          | Higher risk if cache fails before sync |

↓

↓

Database Updated ✅

↓

Response Sent

Write-Back
Update User Name

↓

↓

Response Sent ✅

↓

↓

Database Updated
