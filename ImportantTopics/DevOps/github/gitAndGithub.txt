name: Schedule job ok

on:
  schedule:
    - cron: "0 0 * * *"

jobs:
  run-script:
    runs-on: ubuntu-latest

    steps:
      - name: Print Message
        run: echo "Scheduled Workflow"  



name: Schedule job ok
name → Name of the GitHub Actions workflow.
Here, the workflow name is Schedule job ok.
on:
  schedule:
on → Defines when the workflow will run.
schedule → Runs the workflow automatically at a specified time.
- cron: "0 0 * * *"
cron → Defines the schedule using cron syntax.
"0 0 * * *" → Runs every day at 12:00 AM UTC.
Cron format
minute hour day-of-month month day-of-week

For example:

0 0 * * *
Minute	Hour	Day	   Month	Weekday
0	      0	    Every	Every	     Every
jobs:
jobs → Contains the tasks that the workflow will perform.
run-script:
This is the job name/ID.
runs-on: ubuntu-latest
Specifies the operating system for running the job.
ubuntu-latest means the latest available Ubuntu runner.
steps:
steps → Contains the individual commands executed by the job.
- name: Print Message
Gives a readable name to this step.
run: echo "Scheduled Workflow"
run → Executes a command in the Ubuntu runner.
echo prints the message:
Scheduled Workflow
Flow

Scheduled Time → Workflow Starts → Job Runs → Ubuntu Runner → Print Message

To disable a GitHub Actions workflow, you can do it from GitHub:

Go to your GitHub repository.
Click Actions.
Select your workflow, e.g. Schedule job ok.
Click the ⋯ (three dots) menu.
Select Disable workflow.

The workflow will remain in your repository, but the scheduled job will no longer run.
Another option

Remove or comment out the schedule trigger:

on:
  # schedule:
  #   - cron: "0 0 * * *"

Or remove the workflow YAML file from .github/workflows/.

name: Build My Angular App

on:
  push:
    branches: [main]

jobs:
  build-angular-app:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v6.1.0

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: 22

      - name: Install dependencies
        run: npm install

      - name: Build Angular app
        run: npm run build


These are the 3 important parts:

1. actions/checkout
- name: Checkout code
  uses: actions/checkout@v6.1.0

Meaning: GitHub Actions runner starts with a fresh Ubuntu machine.
checkout downloads your GitHub repository code into that machine.
Without checkout, the runner doesn't have your project files.

2. actions/setup-node
- name: Setup Node.js
  uses: actions/setup-node@v6
  with:
    node-version: 22

Meaning: Installs/configures Node.js 22 on the GitHub Actions machine.

Now commands like:
node
npm

can be used.

3. npm run build
- name: Build Angular app
  run: npm run build

Meaning: Runs the build script from your package.json.
For example:

{
  "scripts": {
    "build": "ng build"
  }
}

So:

npm run build
actually executes:
ng build

and creates the production build of your Angular application.

explanation:
name: Build My Angular App
→ Name of the GitHub Actions workflow.

on:
  push:
    branches: [main]

→ Workflow runs whenever code is pushed to main.

jobs:
  build-angular-app:
→ Defines a job called build-angular-app.

runs-on: ubuntu-latest
→ Job runs on a GitHub-hosted Ubuntu machine.

steps:
→ List of tasks the job will perform.

- name: Checkout code
  uses: actions/checkout@v6.1.0
→ Downloads/checks out your repository code into the runner.

- name: Setup Node.js
  uses: actions/setup-node@v6
  with:
    node-version: 22

→ Installs/configures Node.js 22 on the runner.

- name: Install dependencies
  run: npm install

→ Installs packages from package.json.

- name: Build Angular app
  run: npm run build

→ Runs your Angular build command and checks whether the application builds successfully.

Overall

Push → Ubuntu runner → checkout code → setup Node → install dependencies → build Angular app.

nGitHub Actions, concurrency controls how many workflow runs are allowed to run at the same time.
Example: Only one deployment at a time

name: Build My Angular App

on:
  push:
    branches: [main]

concurrency:
  group: production-deployment
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v6

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: 22

      - name: Install dependencies
        run: npm install

      - name: Build Angular app
        run: npm run build

What happens?

Suppose you push 3 times quickly:

Push 1 → Workflow A starts
Push 2 → Workflow B starts
Push 3 → Workflow C starts

Without concurrency:

A ──────────────────>
B ──────────────────>
C ──────────────────>

All three can run simultaneously.

  With:

concurrency:
  group: production-deployment
  cancel-in-progress: true

you get:

A ─────────X
B ─────X
C ──────────────────>

Only the latest run (C) continues. Older running/pending runs are cancelled.

group
group: production-deployment

This gives your workflow a concurrency group name.
Runs having the same group cannot run concurrently.

cancel-in-progress
cancel-in-progress: true

Means:
If a new run comes, cancel the currently running run.

If you use:
cancel-in-progress: false

the current run finishes, and the newer run waits.

Simple real-world example

For deployment:

concurrency:
  group: production
  cancel-in-progress: true

If you push:

commit A → deploy
commit B → deploy
commit C → deploy

You generally don't want an old commit deploying after a newer commit.
 So GitHub cancels the old deployment and keeps the latest one.

Easy way to remember:
concurrency = "Don't let multiple workflow runs of the same group interfere with each other."
