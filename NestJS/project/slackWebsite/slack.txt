Option 1 — @BeforeInsert() / @BeforeUpdate() ⭐
For your case, this is the simplest approach.

import {
  Entity,
  PrimaryGeneratedColumn,
  Column,
  BeforeInsert,
  BeforeUpdate,
} from 'typeorm';

@Entity('users')
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  email: string;

  @Column()
  password: string;

  @Column({ unique: true })
  username: string;

  @Column({ nullable: true })
  avatar: string;

  @BeforeInsert()
  @BeforeUpdate()
  generateAvatar() {
    this.avatar = `https://robohash.org/${this.username}`;
  }
}
What happens?
When you do:
await userRepository.save(user);

TypeORM does:

save(user)
   ↓
@BeforeInsert()
   ↓
generateAvatar()
   ↓
avatar = https://robohash.org/naeem
   ↓
INSERT into users

For an existing user:

save(user)
   ↓
@BeforeUpdate()
   ↓
generateAvatar()
   ↓
UPDATE users
But there is an important difference

Mongoose:
pre('save')
is a middleware hook.

TypeORM:
@BeforeInsert()
@BeforeUpdate()

are entity lifecycle hooks/listeners.

Option 2 — Subscriber
For more complex logic, use a TypeORM subscriber:
@EventSubscriber()
export class UserSubscriber
  implements EntitySubscriberInterface<User> {
  listenTo() {
    return User;
  }
  beforeInsert(event: InsertEvent<User>) {
    event.entity.avatar =
      `https://robohash.org/${event.entity.username}`;
  }
}
Use a subscriber when the logic is more complicated or you want to keep the Entity clean.

You should throw a GraphQL exception instead of a NestJS HTTP exception:
syntax:throw new GraphQLError(message,{
  extensions:{
    code:metadata
  }
})


import { GraphQLError } from 'graphql';



throw new GraphQLError('Email or username already exists', {
  extensions: {
    code: 'CONFLICT',
    http:{
      status:409
    }
  },
});

//extensions is operational

Yes. The key is understanding that HTTP and GraphQL have different error models.
1. NestJS HTTP exception
When you write:

throw new ConflictException('Email or username already exists');
ConflictException is an HTTP-oriented exception.

It represents:
HTTP 409 Conflict

This makes perfect sense in a REST API:

POST /users
        ↓
duplicate email
        ↓
HTTP 409

The response might be:
{
  "statusCode": 409,
  "message": "Email or username already exists"
}


2. GraphQL works differently
GraphQL normally returns one HTTP endpoint:

POST /graphql
Even if your GraphQL operation has a business error, the HTTP request itself can still be successfully processed.
GraphQL puts the error inside the GraphQL response:
{
  "errors": [
    {
      "message": "Email or username already exists",
      "extensions": {
        "code": "CONFLICT"
      }
    }
  ],
  "data": null
}

So:

HTTP
└── status code → 200
    GraphQL
    └── errors[].extensions.code → CONFLICT

That's the fundamental difference.
How GraphQLError works

You write:

import { GraphQLError } from 'graphql';

throw new GraphQLError(
  'Email or username already exists',
  {
    extensions: {
      code: 'CONFLICT',
    },
  },
);

GraphQLError is an error class from the GraphQL library.
The important part is:

extensions: {
  code: 'CONFLICT',
}

You're adding metadata to the GraphQL error.
Apollo then sends that information to the client:

{
  "errors": [
    {
      "message": "Email or username already exists",
      "extensions": {
        "code": "CONFLICT"
      }
    }
  ]
}
Why did your ConflictException become INTERNAL_SERVER_ERROR?

You had:

throw new ConflictException(
  'Email or username already exists',
);

NestJS knows:

ConflictException
       ↓
HTTP 409

But Apollo doesn't treat NestJS's ConflictException as one of its GraphQL error codes.
So Apollo saw an unrecognized exception and produced:

"extensions": {
  "code": "INTERNAL_SERVER_ERROR"
}

Even though the underlying exception contained:
"statusCode": 409

That's why your previous response had both:

code: INTERNAL_SERVER_ERROR
status: 409

Can you use HTTP exceptions with GraphQL?

Yes, absolutely.
NestJS allows you to use:
BadRequestException
UnauthorizedException
ForbiddenException
NotFoundException
ConflictException

inside GraphQL resolvers/services.
They won't crash the application.

The question is how you want your GraphQL API to expose those errors.

Option 1 — NestJS exceptions
throw new ConflictException('Email already exists');

Simple and familiar if you're already using NestJS.

Option 2 — GraphQL errors
throw new GraphQLError('Email already exists', {
  extensions: {
    code: 'CONFLICT',
  },
});

More naturally aligned with GraphQL's error model.

One important correction
You don't necessarily need to replace every NestJS exception with GraphQLError.

For example, your validation:
new ValidationPipe()

is already producing a BadRequestException, and NestJS/GraphQL is handling that for you.

So you can choose a consistent strategy rather than thinking:
"HTTP exceptions cannot be used in GraphQL."

They can be used. It's just that GraphQL has its own error-response format.

Think of the HTTP layer and GraphQL layer separately.

Request
When a GraphQL query/mutation is sent:

query {
  users {
    id
    name
  }
}

The HTTP request body is roughly:

{
  "query": "query { users { id name } }",
  "variables": {}
}

for mutation:
{
  "query": "mutation { users { id name } }",
  "variables": {}
}

So:
req.body
contains the GraphQL request payload (query, variables, etc.).

➡️ contains the GraphQL query/mutation request payload.
But req.body is not the clean mutation input like Express REST.

Response
Suppose your resolver is:

@Query(() => [User])
users() {
  return [
    { id: 1, name: "Naeem" },
    { id: 2, name: "John" }
  ];
}

Then next.handle() in your interceptor receives the resolver's result:

data = [
  { id: 1, name: "Naeem" },
  { id: 2, name: "John" }
];

If your interceptor does:

map((data) => ({
  success: true,
  message: 'Request successful',
  data,
}))

then GraphQL will use that transformed value as the resolver result.
Conceptually, the final GraphQL response becomes:

{
  "data": {
    "users": {
      "success": true,
      "message": "Request successful",
      "data": [
        {
          "id": 1,
          "name": "Naeem"
        },
        {
          "id": 2,
          "name": "John"
        }
      ]
    }
  }
}

But: your GraphQL schema must allow that response shape. 
You can't arbitrarily add success, message, and data around a resolver that is declared to return [User].

Remember this flow
HTTP Request
     ↓
req.body

{ query, variables }
     ↓
GraphQL
     ↓
Resolver
     ↓
next.handle()
     ↓
data = resolver's return value
     ↓
Interceptor map()
     ↓
GraphQL Response
{ data: ... }


So req.body = GraphQL request, 
while next.handle() → data = resolver result, and GraphQL then builds the final response around it.

and:
res is the HTTP response object.
It does not contain the resolver's returned GraphQL data in the way next.handle() does.
in express it used to response data.

These are common properties you may see on JavaScript/Node.js errors, but not every error has all of them.
1. error.code
Identifies the type/category of error.

Example with MySQL:

error.code === 'ER_DUP_ENTRY'

Means: duplicate value — e.g. trying to insert an email that already exists.

Other examples:

ER_DUP_ENTRY
ER_NO_SUCH_TABLE
ER_ACCESS_DENIED_ERROR

Think: "What kind of error is this?"

2. error.message
Contains the human-readable explanation of the error.

Example:

error.message

Could return:
Duplicate entry 'test@gmail.com' for key 'users.email'
Think: "What exactly went wrong?"

3. error.name

Contains the name/type of the JavaScript error.
Example:
error.name
Could return:

Error
TypeError
ReferenceError
SyntaxError

Example:

try {
  null.someMethod();
} catch (error) {
  console.log(error.name);
}

Output:
TypeError

Think: "What JavaScript error class is this?"

4. error.status
Usually represents an HTTP status code, but it is not guaranteed to exist.

Example:
error.status

Could be:

400
404
500

For example:

throw {
  status: 404,
  message: 'User not found'
};

Think: "What HTTP status should I return?"

5. error.statusCode
Same general idea as status, but commonly used to explicitly mean an HTTP status code.

Example:
error.statusCode

Could be:
400
401
404
500

In NestJS, you'll commonly encounter exceptions such as:

throw new NotFoundException('User not found');
The exception has an HTTP status of:
404
Think: "What HTTP status code should the client receive?"

note->
Some internal/programming errors do not have statusCode at all.
For example:

try {
  const user = await User.findById(id);
} catch (error) {
  console.log(error.statusCode);
}

If the database throws an error, it might look like:

{
  code: "ER_DUP_ENTRY",
  message: "Duplicate entry...",
  name: "Error"
}

There may be no:

statusCode
status

So:

error.statusCode // undefined
Common examples

1. Database error

error.code = "ER_DUP_ENTRY"
error.message = "Duplicate entry..."

❌ statusCode may not exist.

2. Network error

error.code = "ECONNREFUSED"
error.message = "Connection refused"

❌ statusCode may not exist.

3. JavaScript error

error.name = "TypeError"
error.message = "Cannot read properties of undefined"

❌ statusCode usually doesn't exist.

4. NestJS HTTP exception

throw new NotFoundException("User not found");

✅ Has HTTP status 404.

Important concept
Database/Node error
       ↓
may NOT have statusCode
       ↓
your application should assign one
       ↓
500 Internal Server Error

For example:
const statusCode = error.statusCode || 500;

Meaning:
If the error has a statusCode, use it. Otherwise, use 500.
