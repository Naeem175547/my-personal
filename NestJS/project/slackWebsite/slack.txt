Option 1 — @BeforeInsert() / @BeforeUpdate() ⭐
For your case, this is the simplest approach.

import {
  Entity,
  PrimaryGeneratedColumn,
  Column,
  BeforeInsert,
  BeforeUpdate,
} from 'typeorm';

@Entity('users')
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  email: string;

  @Column()
  password: string;

  @Column({ unique: true })
  username: string;

  @Column({ nullable: true })
  avatar: string;

  @BeforeInsert()
  @BeforeUpdate()
  generateAvatar() {
    this.avatar = `https://robohash.org/${this.username}`;
  }
}
What happens?
When you do:
await userRepository.save(user);

TypeORM does:

save(user)
   ↓
@BeforeInsert()
   ↓
generateAvatar()
   ↓
avatar = https://robohash.org/naeem
   ↓
INSERT into users

For an existing user:

save(user)
   ↓
@BeforeUpdate()
   ↓
generateAvatar()
   ↓
UPDATE users
But there is an important difference

Mongoose:
pre('save')
is a middleware hook.

TypeORM:
@BeforeInsert()
@BeforeUpdate()

are entity lifecycle hooks/listeners.

Option 2 — Subscriber
For more complex logic, use a TypeORM subscriber:
@EventSubscriber()
export class UserSubscriber
  implements EntitySubscriberInterface<User> {
  listenTo() {
    return User;
  }
  beforeInsert(event: InsertEvent<User>) {
    event.entity.avatar =
      `https://robohash.org/${event.entity.username}`;
  }
}
Use a subscriber when the logic is more complicated or you want to keep the Entity clean.

You should throw a GraphQL exception instead of a NestJS HTTP exception:
import { GraphQLError } from 'graphql';

throw new GraphQLError('Email or username already exists', {
  extensions: {
    code: 'CONFLICT',
  },
});
Yes. The key is understanding that HTTP and GraphQL have different error models.

1. NestJS HTTP exception

When you write:

throw new ConflictException('Email or username already exists');

ConflictException is an HTTP-oriented exception.

It represents:

HTTP 409 Conflict

This makes perfect sense in a REST API:

POST /users
        ↓
duplicate email
        ↓
HTTP 409

The response might be:

{
  "statusCode": 409,
  "message": "Email or username already exists"
}
2. GraphQL works differently

GraphQL normally returns one HTTP endpoint:

POST /graphql

Even if your GraphQL operation has a business error, the HTTP request itself can still be successfully processed.

GraphQL puts the error inside the GraphQL response:

{
  "errors": [
    {
      "message": "Email or username already exists",
      "extensions": {
        "code": "CONFLICT"
      }
    }
  ],
  "data": null
}

So:

HTTP
└── status code → 200
    GraphQL
    └── errors[].extensions.code → CONFLICT

That's the fundamental difference.

How GraphQLError works

You write:

import { GraphQLError } from 'graphql';

throw new GraphQLError(
  'Email or username already exists',
  {
    extensions: {
      code: 'CONFLICT',
    },
  },
);

GraphQLError is an error class from the GraphQL library.

The important part is:

extensions: {
  code: 'CONFLICT',
}

You're adding metadata to the GraphQL error.

Apollo then sends that information to the client:

{
  "errors": [
    {
      "message": "Email or username already exists",
      "extensions": {
        "code": "CONFLICT"
      }
    }
  ]
}
Why did your ConflictException become INTERNAL_SERVER_ERROR?

You had:

throw new ConflictException(
  'Email or username already exists',
);

NestJS knows:

ConflictException
       ↓
HTTP 409

But Apollo doesn't treat NestJS's ConflictException as one of its GraphQL error codes.

So Apollo saw an unrecognized exception and produced:

"extensions": {
  "code": "INTERNAL_SERVER_ERROR"
}

Even though the underlying exception contained:

"statusCode": 409

That's why your previous response had both:

code: INTERNAL_SERVER_ERROR
status: 409
Can you use HTTP exceptions with GraphQL?

Yes, absolutely.

NestJS allows you to use:

BadRequestException
UnauthorizedException
ForbiddenException
NotFoundException
ConflictException

inside GraphQL resolvers/services.

They won't crash the application.

The question is how you want your GraphQL API to expose those errors.

Option 1 — NestJS exceptions
throw new ConflictException('Email already exists');

Simple and familiar if you're already using NestJS.

Option 2 — GraphQL errors
throw new GraphQLError('Email already exists', {
  extensions: {
    code: 'CONFLICT',
  },
});

More naturally aligned with GraphQL's error model.

One important correction

You don't necessarily need to replace every NestJS exception with GraphQLError.

For example, your validation:

new ValidationPipe()

is already producing a BadRequestException, and NestJS/GraphQL is handling that for you.

So you can choose a consistent strategy rather than thinking:

"HTTP exceptions cannot be used in GraphQL."

They can be used. It's just that GraphQL has its own error-response format.
