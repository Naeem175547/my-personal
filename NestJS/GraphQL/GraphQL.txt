
GraphQL is an open-source query language and runtime for APIs that lets clients request exactly
 the data they need—no more, no less. It was developed by Facebook (now Meta) and released publicly in 2015.

Why use GraphQL?
Compared to REST APIs, GraphQL provides several advantages:

Fetch only the required data: Clients specify exactly which fields they want.
Single endpoint: Instead of multiple REST endpoints, GraphQL typically uses one endpoint (e.g., /graphql).
Reduces over-fetching and under-fetching: Minimizes unnecessary network requests.
Strongly typed schema: The API defines all available types, fields, and operations.
Self-documenting: Tools like GraphQL Playground or GraphiQL can automatically generate API documentation from the schema.
How GraphQL works

A GraphQL API revolves around three main operations:

Query – Retrieve data
Mutation – Create, update, or delete data
Subscription – Receive real-time updates

Example Schema
type User {
  id: ID!
  name: String!
  email: String!
}

type Query {
  user(id: ID!): User
}

Example Query
query {
  user(id: "1") {
    id
    name
    email
  }
}

Response:

{
  "data": {
    "user": {
      "id": "1",
      "name": "John",
      "email": "john@example.com"
    }
  }
}

Notice that the client receives only the requested fields.

Example Mutation
mutation {
  createUser(
    name: "Alice"
    email: "alice@example.com"
  ) {
    id
    name
  }
}
Example Subscription
subscription {
  userCreated {
    id
    name
  }
}

The client stays connected and receives updates whenever a new user is created.

GraphQL vs REST

| Feature        | GraphQL                    | REST                                   |
| -------------- | -------------------------- | -------------------------------------- |
| Endpoints      | Single                     | Multiple                               |
| Data fetching  | Client chooses fields      | Server decides response                |
| Over-fetching  | No                         | Possible                               |
| Under-fetching | No                         | Possible                               |
| Versioning     | Usually not needed         | Often required                         |
| Real-time      | Built-in via subscriptions | Requires WebSockets or other solutions |

When to Use GraphQL
GraphQL is a good choice when:

Frontend applications need flexible data fetching.
Mobile apps need to minimize network usage.
Multiple clients (web, mobile, desktop) require different data shapes.
You want a strongly typed API with excellent developer tooling.

REST may still be preferable for:

Simple CRUD APIs.
Public APIs where HTTP caching is important.
Small applications that don't need flexible querying.

In short, GraphQL gives clients control over the data they receive, making APIs more flexible and efficient than traditional REST APIs in many scenarios.

1. What is a Schema?

A GraphQL schema is a contract between frontend and backend.
It tells the client:
"What data can you request, and what operations can you perform?"
For example, suppose our backend has users.

We define:

type User {
  id: ID!
  name: String!
  email: String!
}

This tells GraphQL:

User
 ├── id
 ├── name
 └── email

The frontend now knows what it can ask for.
User is the name of the Object Type.

type User {
  id: ID!
  name: String!
  email: String!
}



Think of it like a TypeScript class/interface:

interface User {
  id: number;
  name: string;
  email: string;
}

So:

User
 ↓
describes what a User object looks like

id
name
email
 ↓
fields inside User

What does it mean for the frontend?
It tells the frontend:

"If my API gives you a User, these are the fields you can request."
For example, the frontend can ask:

query {
  user {
    id
    name
  }
}

But it cannot ask:

query {
  user {
    phone
  }
}

if phone isn't defined in User.

2. Schema Definition
A GraphQL schema is usually defined using Schema Definition Language (SDL).

Example:

type User {
  id: ID!
  name: String!
  email: String!
}

This is GraphQL SDL.

You can also define the API operations:

type Query {
  users: [User!]!
}

So the complete example becomes:

type User {
  id: ID!
  name: String!
  email: String!
}

type Query {
  users: [User!]!
}

####@ResolveField() in NestJS GraphQL
@ResolveField() is used when you want to resolve a field of an object,
 especially when that field is a nested/related object and its value needs separate logic.

Think:

@Query()
→ resolves the main object


@ResolveField()
→ resolves a field inside that object
Simple example

Suppose you have:

@ObjectType()
export class User {
  @Field(() => Int)
  id: number;


  @Field()
  username: string;


  @Field(() => UserSetting, { nullable: true })
  setting?: UserSetting;
}

You want setting to be fetched separately.
Instead of putting setting directly in users(), you can use:
@Resolver(() => User)
export class UserResolver {


  @Query(() => [User])
  users() {
    return this.userService.getUsers();
  }


  @ResolveField(() => UserSetting, { nullable: true })
  setting(@Parent() user: User) {
    return this.userSettingService.getSettingByUserId(user.id);
  }
}
What happens?

Client asks:

query {
  users {
    id
    username
    setting {
      userId
      receiveNotifications
      receiveEmails
    }
  }
}

Flow:

users()
   ↓
returns Users
   ↓
GraphQL sees "setting"
   ↓
@ResolveField()
   ↓
setting(user)
   ↓
fetch setting using user.id

Why use @ResolveField()?

Suppose:

User
 ├── id
 ├── username
 └── setting

id and username may already exist in the User object.

But setting might come from another table/service/API.

So:

@ResolveField()
setting(...)

lets you fetch it separately.

Important decorators
@ResolveField(() => UserSetting)
setting(@Parent() user: User) {
  // ...
}

do like this

| Part                | Meaning                               |
| ------------------- | ------------------------------------- |
| `@ResolveField()`   | Resolves a field of the parent object |
| `() => UserSetting` | Return GraphQL type                   |
| `setting`           | Field being resolved                  |
| `@Parent()`         | Gets the current `User` object        |


there are two separate things happening here.
i. Can you give the function any name?
Yes. The JavaScript/TypeScript function name does not have to be setting.

For example:

@ResolveField(() => UserSetting, { name: 'setting', nullable: true })
getUserSetting(@Parent() user: User) {
  return mockUsersSetting.find(
    (setting) => setting.userId === user.id
  );
}

This works because GraphQL uses:
name: 'setting'
to decide the GraphQL field name.

So:

getUserSetting()

is the resolver function name in your code, while:

setting

is the field exposed to GraphQL.

If you remove name:

@ResolveField(() => UserSetting)
getUserSetting(@Parent() user: User) {

then NestJS will normally use the method name:

getUserSetting

as the GraphQL field name.

2. How does @Parent() user: User know that it is User data?

This is the important part.

Suppose your User GraphQL type is:

@ObjectType()
export class User {
  @Field(() => Int)
  id: number;


  @Field()
  username: string;


  @Field(() => UserSetting, { nullable: true })
  setting?: UserSetting;
}

And your resolver has:

@Resolver(() => User)
export class UserResolver {}

This:

@Resolver(() => User)

tells NestJS:
"This resolver is resolving fields belonging to the User GraphQL type."

Then:
@ResolveField(() => UserSetting, { name: 'setting' })

means:
"I am providing the resolver for the setting field of User."

So when GraphQL asks:

query {
  users {
    id
    username
    setting {
      theme
    }
  }
}

the flow is roughly:

UserResolver
     ↓
User type
     ↓
setting field requested
     ↓
@ResolveField(... name: "setting")
     ↓
getUserSetting(...)
     ↓
@Parent() user
     ↓
the current User object

What exactly is @Parent()?

@Parent() gives you the parent object currently being resolved.

For example, if your query returns:

[
  { id: 1, username: 'Naeem' },
  { id: 2, username: 'Ali' }
]

When GraphQL resolves setting for the first user:

@Parent() user

is:

{ id: 1, username: 'Naeem' }

For the second:

@Parent() user

is:

{ id: 2, username: 'Ali' }

That's why this works:

setting.userId === user.id
One important correction

@Parent() user: User — the User after the colon is TypeScript typing.

The actual connection to the GraphQL User type comes primarily from:

@Resolver(() => User)

and the field decorator:

@ResolveField(...)

So think:

@Resolver(() => User)
➡️ "I'm resolving fields of User."

@ResolveField(() => UserSetting, { name: 'setting' })
➡️ "I'm resolving User's setting field."

@Parent() user: User
➡️ "Give me the current User object, and TypeScript, treat it as a User."

That's the key idea.

What is a Mutation?

GraphQL has three main operation types:

Query       → Read data
Mutation    → Change data
Subscription → Listen for changes/live changes

For example:

query {
  users {
    id
    username
  }
}

reads data.

But:

mutation {
  createUser(...) {
    id
    username
  }
}

changes data.

Typical mutations:

createUser
updateUser
deleteUser
login
logout
createPost
addComment
likePost


2. Basic Mutation
The simplest mutation can have individual arguments:

@Mutation(() => User)
createUser(
  @Args('username') username: string,
) {
  const user = {
    id: ++incrementalId,
    username,
  };

  mockUsers.push(user);//mockUsers is object
  return user;
}

GraphQL:

mutation {
  createUser(username: "Naeem") {
    id
    username
  }
}

The important part is:

@Mutation(() => User)
means:
This resolver returns a User.

3. Why use ObjectType?
You already have something like:

@ObjectType()
export class User {
  @Field(() => Int)
  id: number;


  @Field()
  username: string;


  @Field({ nullable: true })
  displayName?: string;
}

@ObjectType() describes data that can be returned to the client.

Think:

ObjectType
     ↓
OUTPUT

For example:

mutation {
  createUser(username: "Naeem") {
    id
    username
    displayName
  }
}

GraphQL uses your User ObjectType to know what fields are available.


4. Why InputType?

Now suppose you need to create a user with many fields:

username
password
displayName
email
age

You could do:

createUser(
  @Args('username') username: string,
  @Args('password') password: string,
  @Args('displayName') displayName: string,
  @Args('email') email: string,
  @Args('age') age: number,
)

This becomes messy.
Instead, create an input object:

@InputType()
export class CreateUserInput {
  @Field()
  username: string;


  @Field()
  password: string;


  @Field({ nullable: true })
  displayName?: string;


  @Field({ nullable: true })
  email?: string;
}

Now:

createUser(
  @Args('input') input: CreateUserInput,
) {
  // ...
}

GraphQL:

mutation {
  createUser(
    input: {
      username: "Naeem"
      password: "123"
      displayName: "Naeem"
    }
  ) {
    id
    username
    displayName
  }
}

Much cleaner.
we can write any name in place of input


5. ObjectType vs InputType

Client --------------------> Server
          InputType
             ↓
          Mutation
             ↓
          ObjectType
             ↓
Client <-------------------- Server

Or simply:

InputType  = INPUT
ObjectType = OUTPUT

6. Why can't we use User as input?
You might wonder:

Why not just use User for creating a user?

For example:

createUser(
  @Args('user') user: User
)

GraphQL doesn't allow normal ObjectType classes to be used as input types.

And logically, User and CreateUserInput represent different things.

A User might contain:

id
username
displayName
createdAt
updatedAt

But when creating a user:

id             → generated by server
createdAt      → generated by server
updatedAt      → generated by server
username       → provided by client
password       → provided by client

So you need a separate input type.


9. Create mutation response

GraphQL has another powerful feature.

You don't have to return the entire object.

Suppose mutation returns:

@Mutation(() => User)

The client can request:

mutation {
  createUser(
    input: {
      username: "Naeem"
    }
  ) {
    id
    username
  }
}

Only these fields are returned:

id
username

The server might internally return:

{
  id: 4,
  username: "Naeem",
  password: "123",
  displayName: "Naeem"
}

but GraphQL only sends what the client requested.

10. Create with nested InputType
InputTypes become especially useful with nested data.
Suppose a user has an address.

@InputType()

  @Field()
  city: string;

  @Field()

    username
  }

This is one of the major advantages of InputTypes.

11. Create vs Update Input

You normally shouldn't use the same input for everything.

Create:

@InputType()
class CreateUserInput {
  @Field()
  username: string;


  @Field()
  password: string;


  @Field({ nullable: true })
  displayName?: string;
}

Update:

@InputType()
class UpdateUserInput {
  @Field({ nullable: true })
  username?: string;


  @Field({ nullable: true })
  displayName?: string;
}

Why?

Creating:

username → required
password → required

Updating:

username → optional
password → optional
displayName → optional

Because an update may change only one field.

12. Update Mutation
@Mutation(() => User)
updateUser(
  @Args('id', { type: () => Int }) id: number,
  @Args('input') input: UpdateUserInput,
) {
  const user = mockUsers.find(user => user.id === id);


  if (!user) {
    throw new Error('User not found');
  }
  Object.assign(user, input);
  return user;
}

13. Delete Mutation
Delete usually returns something other than User.
For example:

@Mutation(() => Boolean)

  @Args('id', { type: () => Int }) id: number,

  const index = mockUsers.findIndex(user => user.id === id);

  if (index === -1) {
    return false;
  }  mockUsers.splice(index, 1);
  return true;
}

mutation {

Response:

Here:
@Mutation(() => Boolean)

means:

14. Better Delete Response
In larger applications, returning only Boolean isn't always enough.
You can create an ObjectType:

@ObjectType()
class DeleteUserResponse {
  @Field()
  success: boolean;

  @Field()
  message: string;
}

Then:

@Mutation(() => DeleteUserResponse)
deleteUser(
  @Args('id', { type: () => Int }) id: number,
) {
  const index = mockUsers.findIndex(user => user.id === id);


  if (index === -1) {
    return {
      success: false,
      message: 'User not found',
    };
  }


  mockUsers.splice(index, 1);


  return {
    success: true,
    message: 'User deleted',
  };
}

Client:

mutation {
  deleteUser(id: 1) {
    success
    message
  }
}

This is much more useful for real applications.

What is a Guard?
A Guard runs before your Resolver/Controller handler.

Basic flow:

GraphQL Request
      ↓
    Guard
      ↓
  Allowed?
   ↙     ↘
 Yes      No
  ↓        ↓
Resolver   Error
  ↓
Service

For example, suppose you have:

query {
  profile {
    id
    username
  }
}

You may want only logged-in users to access profile.
The Guard checks:

Is user logged in?
       ↓
    Yes → Resolver executes
       ↓
     No → Reject request

2. CanActivate
In NestJS, a Guard normally implements:

CanActivate

Example:

import {
  CanActivate,
  ExecutionContext,
  Injectable,
} from '@nestjs/common';


@Injectable()
export class AuthGuard implements CanActivate {

  canActivate(context: ExecutionContext): boolean {
    return true;
  }
}

The important method is:
canActivate()

It returns:

true  → allow request
false → reject request

So:

canActivate(): boolean {
  return true;
}

means:

Allow this request.

And:

canActivate(): boolean {
  return false;
}

means:

Don't allow this request.

3. Auth Guard
In a real application, you don't simply return true.
You check authentication.
For example, imagine the user sends a JWT:

Authorization: Bearer <token>

Your Auth Guard checks the token.

Conceptually:

Request
  ↓
AuthGuard
  ↓
JWT valid?
 ↙       ↘
Yes       No
 ↓         ↓
User      Reject
 ↓
Resolver

A simplified example:

@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const token = request.headers.authorization;
    if (!token) {
      return false;
    }
    return true;
  }
}

However, GraphQL is slightly different from REST because the request is accessed through the GraphQL execution context.
You'll commonly see:
GqlExecutionContext
+
Example:

import {
  CanActivate,
  ExecutionContext,
  Injectable,
} from '@nestjs/common';


import { GqlExecutionContext } from '@nestjs/graphql';


@Injectable()
export class AuthGuard implements CanActivate {


  canActivate(context: ExecutionContext): boolean {
    const ctx = GqlExecutionContext.create(context);
    const request = ctx.getContext().req;
    const token = request.headers.authorization;
    return !!token;
  }
}

The important idea is:

GqlExecutionContext
        ↓
      req
        ↓
 authorization header
        ↓
      token

For example:

@Mutation(() => Post)
@UseGuards(AuthGuard)

2. Auth Guard — auth.guard.ts

The Guard gets the request and verifies the JWT.

import {
  CanActivate,
  ExecutionContext,
  Injectable,
  UnauthorizedException,
} from '@nestjs/common';


import { GqlExecutionContext } from '@nestjs/graphql';


import { JwtService } from '@nestjs/jwt';


@Injectable()
export class AuthGuard implements CanActivate {

  constructor(
    private jwtService: JwtService,
  ) {}


  async canActivate(
    context: ExecutionContext,
  ): Promise<boolean>| boolean {


    // 1. Convert normal ExecutionContext
    //    into GraphQL context
    const gqlContext =
      GqlExecutionContext.create(context);

    // 2. Get GraphQL context
    const ctx =
      gqlContext.getContext();


    // 3. Get HTTP request
    const request =
      ctx.req;


    // 4. Get Authorization header
    const authorization =
      request.headers.authorization;


    if (!authorization) {
      throw new UnauthorizedException(
        'Token missing',
      );
    }


    // 5. Get token
    const token =
      authorization.split(' ')[1];


    // 6. Verify JWT
    const payload =
      await this.jwtService.verifyAsync(token);


    // 7. Put authenticated user information
    //    into request
    request.user = payload;


    // 8. Allow Resolver to execute
    return true;
  }
}

The important part is:

request.user = payload;

This is where we put the authenticated user information.

3. What is inside payload?

Suppose when logging in you created the JWT like this:

  email: user.email,
};

  await this.jwtService.signAsync(payload);

Then after verification:

contains approximately:

  sub: 1,
  email: "naeem@example.com"
}

And this:

makes:

available.

Let's learn GraphQL subscriptions from the basic level, using your NestJS + GraphQL + React project.
1. First understand the idea

You already know:

Query
→ Client asks → Server responds


Mutation
→ Client asks server to change something → Server responds


Subscription
→ Client says "keep me updated"
→ Server pushes new data whenever it happens

For your blog, imagine:
Whenever a new post is created, every user who subscribed should receive that post automatically.

2. Basic GraphQL syntax
You already know:

query {
  posts {
    id
    title
  }
}

and:

mutation {
  createPost(...) {
    id
    title
  }
}

Subscription looks similar:

subscription {
  newPost {
    id
    title
    content
  }
}

The important difference is when the response comes.

Query
Client → Server
        ← Data

Subscription
Client → Server
        ← connection stays open


New post
        ← Post


Another post
        ← Post


Another post
        ← Post

3. How NestJS handles subscriptions
In NestJS GraphQL, you create a subscription in your resolver.

For example:

@Subscription(() => Post)
newPost() {
    return this.pubSub.asyncIterableIterator("newPost");
}

But where does pubSub come from?
We use PubSub.

5. Create subscription
Suppose your resolver looks like:

@Resolver(() => Post)
export class PostResolver {
    constructor(
        private readonly postService: PostService,

Now your GraphQL schema has:

type Subscription {
    newPost: Post!
}

"newPost" → PubSub event name
asyncIterableIterator("newPost")
→ keep listening for new data that comes from newPost event

6. Publish when a post is created
Now your mutation creates the post:

@Mutation(() => Post)
async createPost(
    @Args("title") title: string,
    @Args("content") content: string,
) {
    const post = await this.postService.createPost(
        title,
        content,
    );


    await pubSub.publish("newPost", {
        newPost: post,
    });

    return post;
}

This is the important part:
pubSub.publish(
    "newPost",       // event name
    { newPost: post } // payload
);

It means:
"A new post has been created. Tell everyone subscribed to newPost."
he event name and payload property often have the same name for convenience, but technically they are separate things.

publish → "newPost"
subscribe → "newPost"

GraphQL field

     ↓
looks for payload.newPost
     ↓
payload.newPost = post
     ↓
returns Post so newPost properties from newPost event is not returned only its value returned

// ==================== PACKAGES ====================

npm install @apollo/client graphql graphql-ws

// → Provides WebSocket communication for GraphQL subscriptions.
// → createClient() creates the GraphQL WebSocket connection.

// @apollo/client/link/subscriptions
// → GraphQLWsLink connects graphql-ws with Apollo Client.

// @apollo/client/utilities
// → getMainDefinition() identifies whether the operation
//   is a query, mutation, or subscription.


// ==================== apollo.ts ====================

import {
  ApolloClient,
  InMemoryCache,
  HttpLink,
  split,
} from "@apollo/client";

import { GraphQLWsLink } from "@apollo/client/link/subscriptions";

import { createClient } from "graphql-ws";

import { getMainDefinition } from "@apollo/client/utilities";


// HTTP connection
// Used for Query + Mutation

const httpLink = new HttpLink({
  uri: "http://localhost:3000/graphql",
});


// WebSocket connection
// Used for GraphQL Subscription

const wsLink = new GraphQLWsLink(
  createClient({
    url: "ws://localhost:3000/graphql",
  }),
);


// Decide which connection to use

const splitLink = apollo.split(
  ({ query }) => {
    const definition = getMainDefinition(query);
    return (
      definition.kind === "OperationDefinition" &&
      definition.operation === "subscription"
    );

  },

  wsLink,    // Subscription → WebSocket
  httpLink   // Query/Mutation → HTTP
);


// Create Apollo Client

export const client = new ApolloClient({
  link: splitLink,
  cache: new InMemoryCache(),
});


// ==================== main.tsx ====================

import { ApolloProvider } from "@apollo/client/react";
import { client } from "./apollo";

<ApolloProvider client={client}>
  <App />
</ApolloProvider>


// ==================== subscription.ts ====================

import { gql } from "@apollo/client";

export const NEW_POST = gql`
  subscription {
    newPost {
      id
      title
      content
      createdAt
    }
  }
`;


// ==================== Component ====================

import { useSubscription } from "@apollo/client/react";
import { NEW_POST } from "../graphql/subscription";

export default function Posts() {

  const {
    data,
    loading,
    error,
  } = useSubscription(NEW_POST);

  console.log(data);

  if (loading) {
    return <p>Waiting for new posts...</p>;
  }

  if (error) {
    return <p>Error: {error.message}</p>;
  }

  return (
    <div>
      {data?.newPost && (
        <p>
          New post: {data.newPost.title}
        </p>
      )}
    </div>
  );
}

Yes. useSubscription() automatically receives the event whenever a new post is published
. You do not call it again after inserting a post.
