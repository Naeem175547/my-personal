Apollo Client
1. What is Apollo Client?
Apollo Client is a library used in React to communicate
with a GraphQL server.
It helps you:

React
  ↓
Apollo Client
  ↓
GraphQL Server (NestJS)

Without Apollo Client, you would have to manually send HTTP requests
 and manage GraphQL responses.

Apollo Client handles things like:

Sending queries
Sending mutations
Loading state
Error state
Data state
Caching


2. Installation
Inside your React project:
npm install @apollo/client graphql
You need:
@apollo/client → Apollo Client
graphql        → GraphQL library



3. Configuration
Create an Apollo Client:
import { ApolloClient, InMemoryCache } from "@apollo/client";


const client = new ApolloClient({
  uri: "http://localhost:3000/graphql",
  cache: new InMemoryCache(),
});


notes-->
here error is because you're likely using a newer Apollo Client version. In Apollo Client 4, uri is configured through HttpLink, not directly on ApolloClient.

Use this:
import {
  ApolloClient,
  InMemoryCache,
  HttpLink,
} from "@apollo/client";


const httpLink = new HttpLink({
  uri: "http://localhost:3000/graphql",
});


export const client = new ApolloClient({
  link: httpLink,
  cache: new InMemoryCache(),
});


What does this mean?
uri: "http://localhost:3000/graphql"

This is your NestJS GraphQL endpoint.
For example:

React
  ↓
http://localhost:3000/graphql
  ↓
NestJS



And:
cache: new InMemoryCache()
creates Apollo's client-side cache.



4. Provider
React components need access to the Apollo Client.
So we wrap the application with ApolloProvider.

import { ApolloProvider } from "@apollo/client";
import { client } from "./apollo-client";
import App from "./App";


function main() {
  return (
    <ApolloProvider client={client}>
      <App />
    </ApolloProvider>
  );
}

Usually with React/Vite, you'll have something like:

import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { ApolloProvider } from "@apollo/client";
import App from "./App";
import { client } from "./apollo-client";


createRoot(document.getElementById("root")).render(
  <StrictMode>
    <ApolloProvider client={client}>
      <App />
    </ApolloProvider>
  </StrictMode>
);


this is another Apollo Client 4 change. In Apollo Client 4, ApolloProvider is no longer exported from the main @apollo/client package. It comes from @apollo/client/react.
Change:
import { ApolloProvider } from "@apollo/client";
to:
import { ApolloProvider } from "@apollo/client/react";

ApolloProvider

---->GraphQL Queries — useQuery()
Now we connect your React + Apollo Client to the NestJS GraphQL Query.
1. What is useQuery()?

useQuery() is a React hook from Apollo Client used to execute a GraphQL Query and get the result.

React Component
      ↓
   useQuery()
      ↓
Apollo Client
      ↓
NestJS GraphQL
      ↓
Database

2. NestJS Query
Suppose your NestJS resolver has:

@Query(() => [User])
users() {
  return this.userService.getUsers();
}

So GraphQL provides:

type Query {
  users: [User]
}
3. Write the Query in React

Create:

src/
└── graphql/
    └── queries.ts
import { gql } from "@apollo/client";
export const GET_USERS = gql`
  query {
    users {
      id
      username
      displayName
    }
  }
`;
gql converts the GraphQL query into something Apollo Client can use.

4. Use useQuery()
Because you're using Apollo Client 4:

import { useQuery } from "@apollo/client/react";
import { GET_USERS } from "./graphql/queries";


function Users() {
  const { data, loading, error } = useQuery(GET_USERS);
  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error: {error.message}</p>;
  return (
    <div>
      {data?.users.map((user: any) => (
        <div key={user.id}>
          <p>{user.username}</p>
          <p>{user.displayName}</p>
        </div>
      ))}
    </div>
  );
}

export default Users;
useQuery() returns
const { data, loading, error } = useQuery(GET_USERS);
| Value     | Meaning                    |
| --------- | -------------------------- |
| `data`    | Data returned by GraphQL   |
| `loading` | Query is currently running |
| `error`   | Something went wrong       |

Query Variables
Suppose NestJS has:

@Query(() => User, { nullable: true })
user(@Args("id", { type: () => ID }) id: number) {
  return this.userService.getUserById(id);
}

GraphQL query:

query GetUser($id: ID!) {
  user(id: $id) {
    id
    username
    displayName
  }
}

or
you can omit the query name.

Without a name
query ($id: ID!) {
  user(id: $id) {
    id
    username
    displayName
  }
}

Here:

$id → GraphQL variable
$id: ID! → variable type
user(id: $id) → pass variable to query

In React:

const GET_USER = gql`
  query GetUser($id: ID!) {
    user(id: $id) {
      id
      username
      displayName
    }
  }
`;

Then:

const { data, loading, error } = useQuery(GET_USER, {
  variables: {
    id: 10,
  },
});

So the flow is:

variables: { id: 10 }
          ↓
$id = 10
          ↓
user(id: $id)
          ↓
NestJS @Args("id")
          ↓
getUserById(10)

Why variables?
Instead of writing:
user(id: 10)
every time, you create a reusable query:
user(id: $id)

and React can provide different values:
variables: { id: 10 }
or:
variables: { id: 20 }

Remember
useQuery()
    ↓
Execute GraphQL Query


variables
    ↓
Send dynamic values to the Query

$ is necessary when you use GraphQL variables.

GraphQL Mutations
A Mutation is used when you want to change data.

Query     → Read
Mutation  → Create / Update / Delete
1. NestJS Mutation

Suppose your NestJS resolver has:

@Mutation(() => User)
createUser(
  @Args('username') username: string,
  @Args('email') email: string,
) {
  return this.userService.createUser(username, email);
}

GraphQL provides a mutation like:

type Mutation {
  createUser(username: String!, email: String!): User
}
2. React — useMutation()

Apollo provides the useMutation() hook.

import { gql } from "@apollo/client";
import { useMutation } from "@apollo/client/react";


const CREATE_USER = gql`
  mutation {
    createUser(
      username: "Naeem"
      email: "naeem@example.com"
    ) {
      id
      username
      email
    }
  }
`;

Then:
const [createUser] = useMutation(CREATE_USER);
To execute it:

createUser();

Important difference from useQuery()
useQuery(GET_USERS);

The query runs automatically when the component renders.

But:
const [createUser] = useMutation(CREATE_USER);
doesn't execute immediately.
You call:
createUser();

when you want to perform the mutation, usually after a button/form submission.

3. Mutation with Variables ⭐
Hard-coding values isn't good:

mutation {
  createUser(
    username: "Naeem"
    email: "naeem@example.com"
  ) {
    id,
    name
  }
}

Instead, use variables:

const CREATE_USER = gql`
  mutation CreateUser($username: String!, $email: String!) { //CreateUser name is optional as useQuery operation name
    createUser(
      username: $username
      email: $email
    ) {
      id
      username
      email
    }
  }
`;

Then:
const [createUser] = useMutation(CREATE_USER);


createUser({
  variables: {
    username: "Naeem",
    email: "naeem@example.com",
  },
});

Flow:

React
  ↓
createUser()
  ↓
variables
  ↓
GraphQL Mutation
  ↓
NestJS @Mutation()
  ↓
Service
  ↓
MySQL/DB

Why variables?
Because the values usually come dynamically from a form:

createUser({
  variables: {
    username: username,
    email: email,
  },
});

So:

Query
→ useQuery()


Mutation
→ useMutation()


Dynamic values
→ variables

One important point: In real NestJS applications,
 you'll commonly use an InputType for mutations with multiple fields:

createUser(input: CreateUserInput!): User

We'll get to that when you study Input Types.

-->GraphQL InputType

An InputType is a custom structure used to send multiple input values together to a Query or, 
more commonly, a Mutation.
Instead of:
createUser(username: String!, email: String!, age: Int!)
you can create:

input CreateUserInput {
  username: String!
  email: String!
  age: Int!
}

Then:
createUser(input: CreateUserInput!): User

NestJS
import { InputType, Field, Int } from '@nestjs/graphql';

@InputType()
export class CreateUserInput {
  @Field()
  username: string;

  @Field()
  email: string;


  @Field(() => Int)
  age: number;
}

Use it in the resolver:

@Mutation(() => User)
createUser(@Args('input') input: CreateUserInput) {
  return this.userService.createUser(input);
}

React sends
mutation {
  createUser(
    input: {
      username: "Naeem"
      email: "naeem@gmail.com"
      age: 21
    }
  ) {
    id
    username
  }
}

With variables, which is the usual approach:

mutation CreateUser($input: CreateUserInput!) {//we don't defind CreateUserInput inside react it is already in backend
  createUser(input: $input) {
    id

  }
}

React:

createUser({
  variables: {
    input: {
      username: "Naeem",
      email: "naeem@gmail.com",
      age: 21,
    },
  },
});

Without InputType

Caching

Apollo Client has a cache on the React side.
It stores data that was already fetched so Apollo can reuse it instead of requesting the same data from the server again.
NestJS / MySQL
      ↓
   GraphQL
      ↓
 Apollo Client
      ↓
    Cache
      ↓
    React

1. Apollo Cache

You already created it here:
const client = new ApolloClient({
  link: httpLink,
  cache: new InMemoryCache(),
});

InMemoryCache stores GraphQL results in memory.
For example:

query {
  user(id: 1) {
    id
    username
  }
}

Apollo receives:
{
  "id": "1",
  "username": "Naeem"
}

and keeps that data in its cache.

If another component asks for the same data,
 Apollo may use the cached data instead of making another network request.

 2. Cache Updates

Suppose you create a new user:
Existing cache:

users
├── User 1
└── User 2

You run:
createUser().
and the server creates:

User 3
But your cache may still contain:
because use fetch data before createUser

users
├── User 1
└── User 2

So you may need to update the cache.

Apollo provides ways to do this.
A simple approach is to refetch the users query after the mutation.

3. Refetching

Refetching means asking the server for the latest data again.
Example:

const { data, refetch } = useQuery(GET_USERS);

Then:

await createUser({
  variables: {
    input: {
      username: "Naeem",
      email: "naeem@gmail.com",
    },
  },
});


refetch();

Flow:

Create User
    ↓
Database changes
    ↓
refetch()
    ↓
GraphQL server
    ↓
Latest users
    ↓
Apollo cache updates
    ↓
React displays latest data

|                | Cache                   | Refetch                      |
| -------------- | ----------------------- | ---------------------------- |
| Purpose        | Reuse stored data       | Get fresh data               |
| Server request | May not happen          | Happens                      |
| Speed          | Fast                    | Requires network             |
| Example        | Previously fetched user | Refresh users after creation |


Yes, that's the basic idea. ✅

If Apollo already has the required data in its cache, 
another component using useQuery() can get that data from the cache
 instead of needing to fetch it again.

Example
Component A
const { data } = useQuery(GET_USERS);

Server returns:
User 1
User 2

Apollo stores it:

Apollo Cache
    ↓
User 1
User 2

Later, Component B does:

const { data } = useQuery(GET_USERS);

Apollo can use the cached result:

Component B
     ↓
useQuery(GET_USERS)
     ↓
Apollo Cache
     ↓
User 1
User 2

So it may not need another request to NestJS.

But one important point
Whether Apollo uses only the cache or also contacts the server depends
 on the query's fetch policy.

The default behavior can involve both cache and network depending on the situation.
 You can explicitly control it:

useQuery(GET_USERS, {
  fetchPolicy: "cache-first",
});

cache-first means:

Cache has data?
   ↓ YES → use cache
   ↓ NO  → request server

That's the simple caching behavior you should remember for now

Polling

Polling = client repeatedly asks the server for updated data at a fixed interval.

In Apollo:

const { data } = useQuery(GET_NOTIFICATIONS, {
  pollInterval: 5000,
});

5000 = 5 seconds.

So:

Request → wait 5s → Request → wait 5s → Request → ...

No WebSocket or Subscription is required.

Authentication — JWT + Auth Headers + Apollo

This is how you connect React + Apollo + NestJS authentication.

React
  ↓
Apollo Client
  ↓
JWT in Authorization header
  ↓
NestJS Guard
  ↓
Resolver

1. JWT
JWT (JSON Web Token) is a token that the server gives to the user after successful login.

Example:
React
 ↓
login(email, password)
 ↓
NestJS
 ↓
login successful
 ↓
JWT token
 ↓
React stores token

The token might look like:
eyJhbGciOiJIUzI1NiIs...

React then sends this token with future GraphQL requests.


2. Auth Header

The token is normally sent using the HTTP Authorization header:
Authorization: Bearer <JWT_TOKEN>
For example:
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

Bearer means:
"The following value is the authentication token."



3. Apollo Authentication

Apollo needs to automatically attach the JWT to GraphQL requests.
With Apollo Client 4, you can use SetContextLink.

Install nothing extra if you're using the appropriate Apollo Client package exports.

apollo-client.ts
import {
  ApolloClient,
  InMemoryCache,
  HttpLink,
} from "@apollo/client";


import { SetContextLink } from "@apollo/client/link/context";


const httpLink = new HttpLink({
  uri: "http://localhost:3000/graphql",
});


const authLink = new SetContextLink((prevContext) => {
  const token = localStorage.getItem("token");
  return {
    headers: {
      ...prevContext.headers,
      authorization: token ? `Bearer ${token}` : "",
    },
  };
});


export const client = new ApolloClient({
  link: authLink.concat(httpLink),
  cache: new InMemoryCache(),
});

Now every GraphQL request can automatically contain:
Authorization: Bearer JWT_TOKEN

4. Why do we use authLink?

Without it:

React
 ↓
GraphQL request
 ↓
NestJS

The request doesn't automatically contain your JWT.

With authLink:

React
 ↓
Apollo Client
 ↓
authLink
 ↓
adds Authorization header
 ↓
HttpLink
 ↓
NestJS

5. NestJS receives the token

On the NestJS side, your authentication guard can read the token from the request.

Conceptually:

Authorization: Bearer JWT
                ↓
            NestJS Guard
                ↓
          verify JWT
                ↓
          authenticated?
           /        \
         YES        NO
          ↓          ↓
      Resolver     Reject

For GraphQL, the authenticated user is commonly made available through the GraphQL context.

Important distinction
JWT
→ The token


Authorization header
→ Where/how the token is sent


Apollo authentication
→ Automatically attaches the token to requests
Complete picture
              LOGIN
React ─────────────────→ NestJS
  ↑                         │
  │                         ↓
  │                      JWT token
  │                         │
  └─────────────────────────┘
           store token


Future request:


React
  ↓
Apollo Client
  ↓
authLink
  ↓
Authorization: Bearer JWT
  ↓
NestJS
  ↓
Guard
  ↓
Resolver
  ↓
Protected data

One important note: for a real production app, storing JWTs in localStorage has security tradeoffs. A common safer architecture
 is using secure, HttpOnly cookies, depending on your authentication design.

| ----------------- | -------------------------------- |
| `ApolloLink`      | Automatically with every request |

1. ApolloLink — Header with every request
import {
  ApolloClient,
  InMemoryCache,
  HttpLink,
  ApolloLink,
} from "@apollo/client";


const httpLink = new HttpLink({
  uri: "http://localhost:3000/graphql",
});


const authLink = new ApolloLink((operation, forward) => {
  const token = localStorage.getItem("token");

  operation.setContext({
    headers: {
      Authorization: token ? `Bearer ${token}` : "",
    },
  });
  return forward(operation);
});


const client = new ApolloClient({
  link: authLink.concat(httpLink),
  cache: new InMemoryCache(),
});


export default client;

Now:

useQuery(ME);
automatically sends:
Authorization: Bearer TOKEN
with every GraphQL request.

2. context.headers — Header for specific request
No ApolloLink needed.

import { useQuery } from "@apollo/client/react";
import { ME } from "../graphql/query";


export default function Profile() {
  const token = localStorage.getItem("token");


  const { data, loading, error } = useQuery(ME, {
    context: {
      headers: {
        Authorization: `Bearer ${token}`,
      },
    },
  });

  if (loading) return <p>Loading...</p>;
  if (error) return <p>{error.message}</p>;
  return (
    <div>
      <h2>{data?.me.name}</h2>
      <p>{data?.me.username}</p>
    </div>
  );
}

Here the header is sent only with this ME request.

Mutation example
const [createPost] = useMutation(CREATE_POST);


createPost({
  variables: {
    input: postData,
  },
  context: {
    headers: {
      Authorization: `Bearer ${localStorage.getItem("token")}`,
    },
  },
});


In ApolloLink:

const authLink = new ApolloLink((operation, forward) => {
    // ...
    return forward(operation);
});
operation
operation represents the current GraphQL request.

It contains information about the request, such as:

operation
├── query       → GraphQL query/mutation
├── variables   → variables sent
└── context     → headers, etc.

You can modify its context:

operation.setContext({
    headers: {
        Authorization: `Bearer ${token}`,
    },
});

So you're basically saying:
"For this current request, add this header."

forward
forward sends the modified operation to the next Apollo Link.

return forward(operation);

Think of it as:

GraphQL request
      ↓
   authLink
      ↓
  operation
  (add token)
      ↓
   forward()
      ↓
 next link / HttpLink
      ↓
    Server

If you don't call forward(operation), the request won't continue to the server.

Delete Post
    ↓
refetchQueries
    ↓
GET_MY_POSTS runs again
    ↓
Backend returns updated posts
    ↓
Apollo Cache updates
    ↓
Components using GET_MY_POSTS get updated data

So if GET_MY_POSTS is used in your Profile component, and deletion happens in your Post component, it can still update the Profile data through Apollo's cache.

Important: refetchQueries = fetch again + update cache.


refetch()          → need access to refetch
                    → props/context may be needed

refetchQueries     → directly reruns GET_MY_POSTS
                    → no prop drilling/context
