1. What is NestJS?
NestJS = Backend framework for Node.js, mainly built with TypeScript.

Node.js
   ↓
NestJS
   ↓
Express / Fastify

It gives you a structured architecture:

Controller
    ↓
Service
    ↓
Repository / Database

2. Why NestJS?

Express:

app.get("/users", (req, res) => {
   // everything can end up here
});

NestJS:

Controller → handles request
Service    → business logic
Module     → organizes feature
DTO        → validates input
Guard      → authentication/authorization
Pipe       → validation/transformation
Interceptor → request/response processing
Filter     → exception handling

This makes large applications easier to maintain.

NestJS Controller

Definition
A Controller in NestJS is responsible for handling incoming HTTP requests and sending responses.

Client
  ↓
Controller
  ↓
Service
  ↓
Database


Basic Example
import { Controller, Get } from '@nestjs/common';

@Controller('users')
export class UsersController {

  @Get()
  getUsers() {
    return ['Naeem', 'Ali'];
  }
}

Important Parts

1. @Controller('users')
Defines the base route.

@Controller('users')
All routes inside start with:

/users

2. @Get()

Handles a GET request.

@Get()
getUsers() {}

Request:

GET /users

3. @Post()

Handles POST requests.

@Post()
createUser() {}

Request:

POST /users
Parameters

Route parameter:

@Get(':id')
getUser(@Param('id') id: string) {
  return id;
}
GET /users/10

Query parameter:

@Get()
getUsers(@Query('page') page: string) {
  return page;
}
GET /users?page=2

Request body:

@Post()
createUser(@Body() data: any) {
  return data;
}
In NestJS, these two are different:

@Body() x
Gets the entire request body.

@Post()
create(@Body() x) {
  console.log(x);
}

Request:

{
  "name": "Naeem",
  "age": 23
}

x becomes:

{
  name: "Naeem",
  age: 23
}
@Body('name') x

Gets only the name property from the body.

@Post()
create(@Body('name') x) {
  console.log(x);
}

Request:

{
  "name": "Naeem",
  "age": 23
}

x becomes:
"Naeem"

Easy rule
@Body()        → complete body
@Body('name')  → only body.name
@Body('age')   → only body.age

So @Body('name') means "give me the name field from the request body."

--->NestJS Service
Definition: A Service contains the application's business logic 
and performs operations such as processing data, communicating with the database, and implementing application rules.

Basic Example

import { Injectable } from '@nestjs/common';

@Injectable()
export class ProductService {
  private products = [
    { id: 1, name: 'Product 1', price: 100 },
    { id: 2, name: 'Product 2', price: 200 },
    { id: 3, name: 'Product 3', price: 300 },
  ];
  getAllProducts() {
    return this.products;
  }
  getProductById(id: number) {
    return this.products.find((product) => product.id == id);
  }
}

@Injectable()

@Injectable() marks the class as a provider that NestJS can create and inject using Dependency Injection.

Controller + Service
Request

   ↓

   ↓
Database

constructor(private usersService: UsersService) {} this inject services

This tells NestJS:
“I need an instance of UsersService here.”
NestJS automatically creates and provides that instance.

now instance is readonly



Then:
this.usersService.getUsers();

Key Point

Service → handles business logic

    private readonly usersService: UsersService,

Definition: A Module is a class that organizes related controllers, services, providers, and other dependencies

Example:

@Module({
  controllers: [UsersController],
  providers: [UsersService],

Think of it as:

UsersModule
   ├── UsersController
   └── UsersService

Important decorators
@Module({
  imports: [],
  controllers: [],
  providers: [],
  exports: [],
})
imports → imports other modules
controllers → registers controllers
providers → registers services/providers
exports → makes providers available to other modules

Simple definition:
👉 Module = A container that groups related parts of a NestJS application.

note->
if we directory render usersmodule instead of app.module in nestFactory?
No. Normally, NestFactory.create() should receive the root module, which is usually AppModule.

const app = await NestFactory.create(AppModule);

Why not UsersModule?
UsersModule is usually a feature module:

AppModule
 ├── UsersModule
 ├── AuthModule
 └── ProductsModule

So the flow is:

main.ts
   ↓
AppModule
   ↓
UsersModule
   ↓
UsersController
UsersService

If you do:

NestFactory.create(UsersModule);
NestJS can technically start with UsersModule, but you would only get the modules/dependencies connected to that module.
 Your other application modules won't automatically be part of the application.

Rule:
👉 NestFactory.create() → Root Module (AppModule).

Interface

Definition:
 An interface in TypeScript defines the structure/type of an object by specifying
 what properties and their types it should have.

Example:

interface User {
  name: string;
  age: number;
}
const user: User = {
  name: "Naeem",
  age: 23
};

In TypeScript, both interface and type are used to define the shape/type of data. They overlap a lot, but there are some important differences.

1. Basic example
interface
interface User {
  id: number;
  username: string;
  email: string;
}
type
type User = {
  id: number;
  username: string;
  email: string;
};

For this simple case, they behave almost the same.
2diffrence
| Feature               |   `interface`   | `type` |
| --------------------- | :-------------: | :----: |
| Object shape          |        ✅        |    ✅   |
| Can be extended       |        ✅        |    ✅   |
| `extends` keyword     |        ✅        |    ❌   |
| Intersection `&`      | ⚠️ Not directly |    ✅   |
| Union `\|`            |        ❌        |    ✅   |
| Primitive types       |        ❌        |    ✅   |
| Tuples                |        ❌        |    ✅   |
| Declaration merging   |        ✅        |    ❌   |
| Functions             |     Limited     |    ✅   |
| Classes can implement |        ✅        |    ✅   |

3. Extending

With interface, use extends:

interface User {
  name: string;
}

interface Admin extends User {
  admin: boolean;
}

Now Admin has:

name
admin

With type, use intersection &:

type User = {
  name: string;
};

type Admin = User & {
  admin: boolean;
};

Same idea.

4. Union types — advantage of type

A type can represent a union:

type Status = 'pending' | 'success' | 'failed';

Now:

let status: Status;

status = 'success'; // ✅
status = 'hello';   // ❌

You cannot do this directly with an interface.

5. Primitive types

type can define primitive aliases:

type UserId = number;
type Username = string;
type IsActive = boolean;

An interface is mainly for describing object-like structures.

6. Tuples

type can easily define tuples:

type UserData = [number, string, string];

Example:

const user: UserData = [1, 'Naeem', 'naeem@gmail.com'];
7. Declaration merging — advantage of interface

This is an important difference.

You can declare the same interface twice:

interface User {
  name: string;
}

interface User {
  age: number;
}

TypeScript merges them.

So User becomes:

interface User {
  name: string;
  age: number;
}

With type, you cannot redeclare the same type:

type User = {
  name: string;
};

type User = {
  age: number;
};

❌ Duplicate identifier error.

8. In NestJS, you'll see both

For example, your CreateUserParams could be a type:

export type CreateUserParams = {
  username: string;
  password: string;
  createdAt: Date;
};

Or an interface:

export interface CreateUserParams {
  username: string;
  password: string;
  createdAt: Date;
}

Both work for this use case.

9. Which should you use?

A simple rule:

Use interface for object contracts
interface User {
  id: number;
  username: string;
  email: string;
}

Especially when you expect the shape to be extended.

Use type for unions, intersections, tuples, and more complex type combinations
type Status = 'pending' | 'success' | 'failed';
type Admin = User & {
  permissions: string[];
};
⭐ Easy way to remember
interface → object structure / contract

type      → flexible type combinations

Neither is universally "better". In modern TypeScript, both are commonly used, and the choice often depends on the situation and project conventions.


Interface vs DTO
Interface → mainly used for TypeScript type checking
DTO → used to define API data structure, and can also support runtime validation with decorators.

In short:
👉 Interface = Defines the shape of an object at TypeScript compile time.

If you add a property that is not defined in an interface or DTO, the behavior depends on which one you're using.

1. Interface
interface User {
  name: string;
  age: number;
}

const user: User = {
  name: "Naeem",
  age: 23,
  email: "test@gmail.com" // ❌ Error
};

TypeScript gives an error because email isn't part of User.

2. NestJS DTO
class CreateUserDto {
  name: string;
  age: number;
}

Request:

{
  "name": "Naeem",
  "age": 23,
  "email": "test@gmail.com"
}

By default, the extra email may still come through.

If you enable:

new ValidationPipe({
  whitelist: true
})

NestJS removes properties that aren't defined in the DTO.

Request
 ↓
{name, age, email}
 ↓
ValidationPipe
 ↓
{name, age}

So:

Interface → extra properties can cause TypeScript errors in object literals.
DTO + whitelist: true → extra request properties are removed.

Apply whitelist: true in the global ValidationPipe, usually inside main.ts.

import { ValidationPipe } from '@nestjs/common';

  const app = await NestFactory.create(AppModule);

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
    }),
  );

  await app.listen(3000);
}

bootstrap();

What it does
If your DTO is:

export class CreateUserDto {
  name: string;
  age: number;
}

Request:

{
  "name": "Naeem",
  "age": 23,
  "email": "test@gmail.com"
}

With whitelist: true:

{
  "name": "Naeem",
  "age": 23
}

👉 Extra properties are removed.

#forbidNonWhitelisted: true
Instead of removing extra properties, it throws an error.

  whitelist: true,
  forbidNonWhitelisted: true,
})

So:

Extra property
      ↓
whitelist: true
      ↓
Remove it


Extra property
      ↓

      ↓
❌ Throw error

Together

    whitelist: true,
    forbidNonWhitelisted: true,

👉 whitelist = remove extra fields
👉 forbidNonWhitelisted = reject extra fields


Important: whitelist works with class-validator decorators,
 so normally your DTO properties should have validation decorators such as @IsString(), @IsInt(), etc.

In NestJS, lifecycle methods are special methods or Hook
 that NestJS calls automatically at specific stages of your application's/module's life.
 Application starts → initialize → run → application shuts down

 | Lifecycle Hook              | When it runs                               | Common use                               |
| --------------------------- | ------------------------------------------ | ---------------------------------------- |
| `OnModuleInit`              | After a module's dependencies are resolved | Initialization logic                     |
| `OnApplicationBootstrap`    | After all modules are initialized          | Start tasks after the whole app is ready |
| `OnModuleDestroy`           | When a module is being destroyed           | Cleanup module resources                 |
| `BeforeApplicationShutdown` | Before the application shuts down          | Prepare for shutdown                     |
| `OnApplicationShutdown`     | When the application is shutting down      | Final cleanup                            |

2. OnModuleInit
Runs when the module has been initialized.

import {
  Injectable,
  OnModuleInit,
} from '@nestjs/common';


@Injectable()
export class UserService implements OnModuleInit {

    console.log('UserService initialized');
  }
}

When NestJS starts:

    ↓
Application continues

NestJS Interceptor

An Interceptor is a class that can run before and/or after a controller method.

Think of it like a wrapper around your controller:

Request
   ↓
Interceptor (before)
   ↓
Controller
   ↓
Interceptor (after)
   ↓
Response

It is commonly used for:

Logging
Measuring execution time
Transforming responses
Adding extra data
Handling/cache-related logic
Working with RxJS streams


1. Basic Interceptor
import {
  Injectable,
  NestInterceptor,
  ExecutionContext,
  CallHandler,
} from '@nestjs/common';


import { Observable } from 'rxjs';


@Injectable()
export class LoggingInterceptor implements NestInterceptor {


  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> {
    console.log('Before controller');
    return next.handle();
  }
}

The important part is:

return next.handle();

It means:

Continue to the controller.

2. Before and After Controller

To execute something after the controller, use RxJS tap().

import {
  Injectable,
  NestInterceptor,
  ExecutionContext,
  CallHandler,
} from '@nestjs/common';


import { Observable, tap } from 'rxjs';


@Injectable()
export class LoggingInterceptor implements NestInterceptor {

  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> {
    console.log('Before controller');
    return next.handle().pipe(
      tap(() => {
        console.log('After controller');
      }),
    );
  }
}

Flow:

Request
   ↓
Before controller
   ↓
Controller executes
   ↓
After controller
   ↓
Response


3. Applying Interceptor to Controller

Use @UseInterceptors().

import { Controller, Get, UseInterceptors } from '@nestjs/common';


@Controller('users')
@UseInterceptors(LoggingInterceptor)
export class UserController {

  getUsers() {
    return [
      { id: 1, name: 'Naeem' },

  }

Now every route in this controller uses the interceptor.

One of the most useful interceptor features is modifying the controller's response.
Suppose controller returns:

@Injectable()

Advanced Use Cases of NestJS Interceptors
Once you understand logging, timing, and response mapping,
 interceptors become useful for cross-cutting concerns that apply to many controllers/resolvers.

1. Caching with Interceptor
Cache expensive responses so you don't query the database every time.

import {
  CallHandler,
  ExecutionContext,
  Injectable,
  NestInterceptor,
} from '@nestjs/common';
import { Observable, of } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class CacheInterceptor implements NestInterceptor {
  private cache = new Map<string, any>();

  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> {
    const request = context.switchToHttp().getRequest();

    const key = request.url;

    // Check cache
    if (this.cache.has(key)) {
      console.log('Returning from cache');
      return of(this.cache.get(key));
    }

    // Execute controller
    return next.handle().pipe(
      tap((data) => {
        console.log('Saving response to cache');
        this.cache.set(key, data);
      }),

    );
  }
}

Flow:

Request
   ↓
Interceptor
   ↓
Cache exists?
   ├── YES → Return cache
   │
   └── NO
        ↓
     Controller
        ↓
     Database
        ↓
     Save response
        ↓
     Client

In production, you'd normally use Redis instead of an in-memory Map.

3. Request ID / Correlation ID
Very useful in production.
Every request gets a unique ID.

import {
  CallHandler,
  ExecutionContext,
  Injectable,
  NestInterceptor,
} from '@nestjs/common';

import { randomUUID } from 'crypto';
import { Observable } from 'rxjs';

@Injectable()
export class RequestIdInterceptor
  implements NestInterceptor {
  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> {

    const request =
      context.switchToHttp().getRequest();

    const response =
      context.switchToHttp().getResponse();

    const requestId =
      randomUUID();

    request.requestId = requestId;

    response.setHeader(
      'X-Request-ID',
      requestId,
    );

    console.log(
      `Request ${requestId} started`,
    );

    return next.handle();
  }
}

Now your logs can show:

Request 7c8f... started
Request 7c8f... UserService called
Request 7c8f... Database query
Request 7c8f... completed

This is extremely useful when debugging distributed applications.

4. Exception Logging
An interceptor can observe errors using RxJS catchError().

import {
  CallHandler,
  ExecutionContext,
  Injectable,
} from '@nestjs/common';

import { Observable, throwError } from 'rxjs';
import { catchError } from 'rxjs/operators';

@Injectable()
export class ErrorLoggingInterceptor {

  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> {

    return next.handle().pipe(

      catchError((error) => {
        console.error(
          'Error:',
          error.message,
        );
        console.error(
          'Stack:',
          error.stack,
        );
        return throwError(() => error);
      }),

    );
  }
}

Important:
return throwError(() => error);

means:
Log the error, but don't swallow it. Let Nest's exception handling continue.

5. Measuring Database/Service Performance
Suppose your handler performs an expensive operation.

return next.handle().pipe(

  tap(() => {
    console.log(
      `Total execution: ${Date.now() - start}ms`,
    );
  }),

);

You can extend this to monitor slow requests:

import {
  CallHandler,
  ExecutionContext,
  Injectable,
} from '@nestjs/common';

import { Observable } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class SlowRequestInterceptor {

  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> {

    const start = Date.now();

    return next.handle().pipe(

      tap(() => {
        const duration =
          Date.now() - start;
        if (duration > 1000) {
          console.warn(
            `Slow request: ${duration}ms`,
          );
        }

      }),

    );
  }
}

This is useful for finding performance problems.

7. Role-Based Response Filtering
You can modify the response based on the authenticated user.

Suppose:

request.user = {
  id: 1,
  role: 'USER'
};

Interceptor:

import {
  CallHandler,
  ExecutionContext,
  Injectable,
} from '@nestjs/common';

import { Observable } from 'rxjs';
import { map } from 'rxjs/operators';

@Injectable()
export class UserResponseInterceptor
  implements NestInterceptor {
  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> {
    const request =
      context.switchToHttp().getRequest();
    const user = request.user;

    return next.handle().pipe(
      map((data) => {
        if (user?.role === 'USER') {
          delete data.password;
        }

        return data;
      }),

    );
  }
}

However, don't rely on this as your main authorization/security mechanism.
 Use guards and proper DTO/serialization strategies for security-sensitive data.

8. Timeout Interceptor
You can prevent a request from hanging indefinitely.

import {
  CallHandler,
  ExecutionContext,
  Injectable,
  RequestTimeoutException,
} from '@nestjs/common';

import { Observable, throwError } from 'rxjs';
import {
  catchError,
  timeout,
} from 'rxjs/operators';

@Injectable()
export class TimeoutInterceptor
  implements NestInterceptor {

  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> {

    return next.handle().pipe(
      timeout(5000),
      catchError((error) => {
        if (error.name === 'TimeoutError') {
          return throwError(
            () =>
              new RequestTimeoutException(
                'Request took too long',
              ),
          );

        }
        return throwError(() => error);
      }),

    );
  }
}

Flow:

Request
   ↓
Interceptor
   ↓
Controller/Resolver
   ↓
Service
   ↓
5 seconds?
   ├── Finished → Response
   │
   └── Not finished → TimeoutException

                    Request

10. The Most Important Advanced Pattern
The most important concept to understand is this:

return next.handle().pipe(
  map(...),
  tap(...),
  catchError(...),
);

Think of it as a pipeline:

                 next.handle()
                      ↓
                  Controller
                      ↓
                    data
                      ↓
                    map()
                      ↓
                transformed
                      ↓
                    tap()
                      ↓
                catchError()
                      ↓
                   response
What each operator does
map()
→ Change the data

tap()
→ Do something without changing the data

catchError()
→ Observe/handle errors

timeout()
→ Limit execution time

of()
→ Return a value without executing handler




important:
If you are using GraphQL Resolver instead of a REST Controller, an interceptor works in the same basic way.

GraphQL Request
      ↓
Interceptor (before)
      ↓
Resolver
      ↓
Interceptor (after)
      ↓
GraphQL Response

REST → interceptor wraps the controller handler
GraphQL → interceptor wraps the resolver handler

DEPENDENCY INJECTION (DI) IN NESTJS
===================================

1. WHAT IS A DEPENDENCY?
========================

A dependency is something a class needs to do its work.

Example:

class UserService {
  constructor(private database: DatabaseService) {}
}

Here:

UserService
    ↓
needs
    ↓
DatabaseService

DatabaseService is a DEPENDENCY of UserService.


2. WHAT IS DEPENDENCY INJECTION?
================================

Dependency Injection means:

Instead of creating the required object yourself,
NestJS creates it and gives it to your class.

Without DI:

class UserService {

  private database = new DatabaseService();

}


With DI:

class UserService {

  constructor(
    private database: DatabaseService
  ) {}

}

NestJS creates DatabaseService
and injects it into UserService.


3. WHY DO WE NEED DI?
=====================

Without DI:

class UserService {

  private database = new DatabaseService();

}

Problems:

- Class creates its own dependency
- Harder to test
- Tightly coupled
- Difficult to replace dependency


With DI:

class UserService {

  constructor(
    private database: DatabaseService
  ) {}

}

Benefits:

- Loose coupling
- Easy testing
- Easy replacement
- NestJS manages dependencies


4. SIMPLE REAL-LIFE EXAMPLE
===========================

Imagine:

Car needs Engine.

Car
 ↓
needs
 ↓
Engine

Instead of Car creating Engine itself:

class Car {
  engine = new Engine();
}

We let someone provide Engine:

class Car {
  constructor(private engine: Engine) {}
}

NestJS acts as the system that provides Engine.

}

//use:
constructor(
  @Inject('CONFIG') private config: any,
) {}


//now config=useValue

20. useClass
============
Used when you want NestJS to use a specific class.

{
  provide: 'DATABASE',
  useClass: MySQLDatabase
}


21. useFactory
==============

Used when the dependency needs to be created
using a function.

{
  provide: 'DATABASE',
  useFactory: () => {
    return createDatabase();
  }
}

useFactory is used when NestJS should call a function to create the dependency.

{
  provide: 'DATABASE',
  useFactory: () => {
    return createDatabase();
  }
}

Meaning:

'DATABASE'
    ↓
call useFactory()
    ↓
createDatabase()
    ↓
returned object
    ↓
inject into service

Then:
constructor(
  @Inject('DATABASE') private database: any
) {}

database receives the value returned by createDatabase()

Main difference
useValue   → already have the value
useClass   → NestJS creates a class instance
useFactory → function creates the value

Important: useFactory becomes especially useful when you need environment variables or other dependencies to create the value.


22. useExisting
===============

Used when you want to use an already registered
provider instead of creating another instance.

useExisting means: use the same instance of an already registered provider.

{
  provide: 'LOGGER',
  useExisting: LoggerService
}

Suppose:

providers: [
  LoggerService,
  {
    provide: 'LOGGER',
    useExisting: LoggerService,
  },
]

Now both refer to the same instance:
@Inject('LOGGER')
logger

and
constructor(private loggerService: LoggerService) {}


23. @Inject()
===========

For normal class injection:

constructor(
  private userService: UserService
) {}


For custom token:

constructor(
  @Inject('DATABASE')
  private database: any
) {}


@Inject() tells NestJS exactly which
dependency/token to inject.


24. TOKEN
=========

A token is the identifier NestJS uses
to find a dependency.

Example:

{
  provide: 'DATABASE',
  useClass: MySQLDatabase
}

'DATABASE'
    ↓
  TOKEN

MySQLDatabase
    ↓

25. INTERFACE + DI
=================

TypeScript interfaces disappear at runtime.
Example:

interface Database {
  findUsers(): any[];
}


You cannot normally do:

constructor(
  private database: Database
) {}


because NestJS cannot use the interface
as a runtime injection token.


Instead:

{
  provide: 'DATABASE',
  useClass: MySQLDatabase
}


Then:

constructor(
  @Inject('DATABASE')
  private database: Database
) {}


26. DI WITH INTERFACE
=====================

interface Database {
  findUsers(): any[];
}


class MySQLDatabase implements Database {

  findUsers() {
    return [];
  }

}

{
  provide: 'DATABASE',
  useClass: MySQLDatabase
}


Injection:

constructor(
  @Inject('DATABASE')
  private database: Database
) {}

UserService
     ↓
'DATABASE'
     ↓
MySQLDatabase


27. MODULE EXPORTS
==================

A provider registered inside one module
is normally available only in that module.

Example:

@Module({
  providers: [UserService],
  exports: [UserService]
})

exports means:
"Other modules are allowed to use UserService."


28. IMPORTING MODULE
====================

Another module can import UserModule:
@Module({
  imports: [UserModule]
})
export class AppModule {}


Now exported UserService can be injected
where available.


29. @Global()
============

A module can be made global:

@Global()
@Module({
  providers: [DatabaseService],
  exports: [DatabaseService]
})
export class DatabaseModule {}


Then other modules don't need to import
DatabaseModule individually.

============

If you see:
Nest can't resolve dependencies of UserService
It usually means NestJS cannot find
one of UserService's dependencies.

Example:
UserService needs:
DatabaseService
but DatabaseService was not registered.
Fix:

@Module({
  providers: [
    UserService,

  ]

    → Invalid request/input

    → User is not authenticated
    → 401

ForbiddenException
    → User does not have permission
    → 403

ConflictException
    → Duplicate/conflicting data
    → 409


========================================================
2. EXCEPTION FILTER
========================================================

Exception Filter is used to catch exceptions and customize
how they are handled.

Basic structure:

import {
  ArgumentsHost,
  Catch,
  ExceptionFilter,
  HttpException,
} from '@nestjs/common';

@Catch(HttpException)
export class FiltersFilter implements ExceptionFilter {

  catch(exception: HttpException, host: ArgumentsHost) {

    const res = host.switchToHttp().getResponse();

    const status = exception.getStatus();

    res.status(status).json({
      statusCode: status,
      message: exception.getResponse(),
      timestamp: new Date().toISOString(),
    });

  }
}

res is used for rest response not graphql response


========================================================
3. @Catch()
========================================================

@Catch(HttpException)

→ Catches only HttpException and its subclasses.

Examples:

NotFoundException
BadRequestException
UnauthorizedException
ForbiddenException
ConflictException


@Catch()

→ Catches all exceptions.

Example:

@Catch()
export class FiltersFilter implements ExceptionFilter {

  catch(exception: unknown, host: ArgumentsHost) {

  }

}


========================================================
4. WHY exception: unknown?
========================================================

If we write:

catch(exception: unknown, host: ArgumentsHost)

TypeScript does NOT know what type exception is.

Therefore this is not directly allowed:

exception.getStatus();


Because unknown may be anything.

If we specifically catch HttpException:

@Catch(HttpException)

catch(exception: HttpException, host: ArgumentsHost)

Now this is allowed:

exception.getStatus();


========================================================
5. ArgumentsHost
========================================================

  ExceptionFilter receives:

  catch(exception, host)


  ArgumentsHost gives information about the context
  where the exception happened.

  It can represent:

  HTTP
  GraphQL
  WebSocket
  RPC


For normal HTTP:

const response = host
  .switchToHttp()
  .getResponse();


This gives the HTTP response object.

   ↓

GraphQL:

   ↓

Therefore:

is mainly for HTTP/REST.

Roles in NestJS = Authorization (what a user is allowed to do).

Authentication:
JwtGuard → checks whether the JWT is valid and identifies the user.

Authorization:
RolesGuard → checks whether the authenticated user has the required role.

Example:

enum Role {
  USER = 'USER',
  ADMIN = 'ADMIN',
}

Roles decorator:

export const Roles = (...roles: Role[]) =>
  SetMetadata('roles', roles);

Admin-only resolver:

@UseGuards(JwtGuard, RolesGuard)
@Roles(Role.ADMIN)
@Mutation(() => Boolean)
updatePostAdmin(...) {
  return this.postService.updateAdmin(...);
}

Flow:

Request
  ↓
JwtGuard → Is the user authenticated?
  ↓
req.user
  ↓
RolesGuard → Does user have required role?
  ↓
ADMIN → Allow
USER  → Reject

Remember:
JwtGuard = Who are you?
RolesGuard = What are you allowed to do?

For user-specific operations, also check ownership:
post.userId === user.id

3. RolesGuard
// common/guards/roles.guard.ts

import {
  CanActivate,
  ExecutionContext,
  Injectable,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { GqlExecutionContext } from '@nestjs/graphql';
import { Role } from '../enums/role.enum';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(context: ExecutionContext): boolean {
    const requiredRoles =
      this.reflector.getAllAndOverride<Role[]>(
        'roles',
        [
          context.getHandler(),
          context.getClass(),
        ],
      );

    if (!requiredRoles) return true;
    const gqlContext = GqlExecutionContext.create(context);
    const user = gqlContext.getContext().req.user;
    if (!user) return false;
    return requiredRoles.includes(user.role);
  }
}


Reflector
Reflector reads the metadata created by your @Roles() decorator.
means:
"Get the value stored under the roles key, and treat that value as a Role[] array."

When you write:

Reflector reads that information.


context.getHandler()
Gets the current method.

1. What is a WebSocket?
Normally with HTTP/graphql:

Client ───── request ─────> Server
Client <──── response ───── Server

The client has to make a request.
With WebSocket:
Client <════════ WebSocket connection ════════> Server

The connection stays open.
So the server can send data to the client whenever something happens, without waiting for a new HTTP request.

This is useful for:
💬 Chat
🔔 Notifications
🟢 Online/offline status
📊 Live dashboards
🎮 Multiplayer games
📍 Live location
⚡ Real-time updates

2. NestJS WebSocket Architecture
In NestJS, the main component is a Gateway.

Client
   ↕
WebSocket
   ↕
Gateway
   ↕
Service
   ↕
Database

The Gateway is similar to a Controller, but instead of handling HTTP routesor graphQL resovler, it handles WebSocket events.

HTTP:
@Controller('users')
export class UserController {}

WebSocket:
@WebSocketGateway()
export class ChatGateway {}

step-4.broadcasting — sending a message to multiple clients.

1. What is broadcasting?
Suppose we have three clients:

User A
User B
User C

User A sends:
"Hello everyone!"

We want:

              ┌──→ User A
User A ──→ Gateway ──→ User B
              └──→ User C

The Gateway sends the message to multiple connected clients.

2. server.emit() — send to everyone
In NestJS, we can use @WebSocketServer() to get the Socket.IO server.

import {
  WebSocketGateway,
  WebSocketServer,
  SubscribeMessage,
  MessageBody,
} from '@nestjs/websockets';


import { Server } from 'socket.io';

@WebSocketGateway()
export class ChatGateway {
  @WebSocketServer()
  server: Server;

  @SubscribeMessage('message')
  handleMessage(
    @MessageBody() message: string,
  ) {
    this.server.emit('message', {
      message,
    });
  }
}


What happens?
User A sends:
message → "Hello"

Then:
this.server.emit('message', {
  message: 'Hello',
});

sends it to:

User A ✅
User B ✅
User C ✅

So:

                  ┌──→ User A
                  │
User A → Gateway ├──→ User B
                  │
                  └──→ User C

3. server.emit() vs client.emit()
This distinction is very important.

client.emit()
client.emit('message', data);

Sends to one specific client.
Gateway
   │
   └────→ User A

server.emit()
this.server.emit('message', data);

Sends to all connected clients.
             ┌──→ User A
             │
Gateway ─────┼──→ User B
             │
             └──→ User C



4. What about the sender?
With:
this.server.emit('message', data);
the sender also receives the message.

So if User A sends:
Hello

all three get it:
User A → "Hello" ✅
User B → "Hello" ✅
User C → "Hello" ✅

  @SubscribeMessage('joinRoom')
  joinRoom(
    @MessageBody() room: string,
    @ConnectedSocket() client: Socket,
  ) {
    client.join(room);
    return {
      message: `Joined ${room}`,
    };
  }


  @SubscribeMessage('leaveRoom')
  leaveRoom(
    @MessageBody() room: string,
    @ConnectedSocket() client: Socket,
  ) {
    client.leave(room);

    return {
      message: `Left ${room}`,
    };
  }

  sendMessage(
    @MessageBody() data: { room: string; message: string },

bcrypt is used to securely hash passwords before storing them in the database.

const hash = await bcrypt.hash(password, 10);
password → original password
10 → salt rounds
hash → encrypted-looking password stored in DB

For login:
await bcrypt.compare(password, hash);

➡️ Checks whether the entered password matches the stored hash.
Match → true
No match → false


salt value:
Lower (e.g. 5) → faster, but less resistant to brute-force attacks.
Higher (e.g. 12) → slower, but stronger.
10 → common starting value for development. 
12 → commonly reasonable for production, depending on server performance.


| Function               | Meaning                            |
| ---------------------- | ---------------------------------- |
| `bcrypt.hash()`        | **Async** → returns a Promise      |
| `bcrypt.hashSync()`    | **Sync** → returns result directly |
| `bcrypt.compare()`     | **Async** → returns a Promise      |
| `bcrypt.compareSync()` | **Sync** → returns result directly |

In NestJS, crypto usually means Node.js's built-in crypto module.
It is used for things like:

🔐 Hashing passwords
🔑 Generating random tokens
🔒 Encryption/decryption
🔢 Generating OTPs
🧂 Creating salts

Example:
import * as crypto from 'crypto';

const hash = crypto
  .createHash('sha256')
  .update('password123')
  .digest('hex');

Important: For storing user passwords, prefer bcrypt/argon2 rather than plain crypto.createHash().

in one short all example
import * as crypto from 'crypto';

// Hash
const hash = crypto.createHash('sha256').update('password').digest('hex');

// Random token
const token = crypto.randomBytes(32).toString('hex');

// OTP
const otp = crypto.randomInt(100000, 1000000).toString();

// UUID
const id = crypto.randomUUID();

Crypto = hashing + random token + OTP + UUID + encryption/decryption.

what fun what is doing
In your example, each function does this:

crypto.createHash('sha256')
➡️ Creates a SHA-256 hash object.

.update('password')
➡️ Gives the data to be hashed.

.digest('hex')
➡️ Produces the final hash as a hexadecimal string.

crypto.randomBytes(32)
➡️ Generates 32 random bytes → useful for secure tokens.

.toString('hex')
➡️ Converts those bytes into a readable hexadecimal string.

crypto.randomInt(100000, 1000000)
➡️ Generates a random number from 100000 to 999999 → useful for a 6-digit OTP.

.toString()
➡️ Converts the number to a string.

crypto.randomUUID()
➡️ Generates a unique UUID, e.g.

In one line

Node mailer
Nodemailer configuration in NestJS, a clean setup is to keep it inside your MailModule.

1. Install Nodemailer
npm install nodemailer
npm install -D @types/nodemailer
2. mail.service.ts

import { Injectable } from '@nestjs/common';
import * as nodemailer from 'nodemailer';

@Injectable()
export class MailService {
  private transporter = nodemailer.createTransport({
    host: process.env.MAIL_HOST,
    port: Number(process.env.MAIL_PORT),
    secure: false,
    auth: {
      user: process.env.MAIL_USER,
      pass: process.env.MAIL_PASSWORD,
    },
  });

  async sendMail(to: string, subject: string, body: string) {
    return await this.transporter.sendMail({
      from: process.env.MAIL_FROM,
      to,
      subject,
      body,
    });
  }
}
3. .env

For example, with an SMTP provider:

MAIL_HOST=smtp.example.com
MAIL_PORT=587
MAIL_USER=your-email@example.com
MAIL_PASSWORD=your-password
MAIL_FROM=your-email@example.com

Don't hard-code the password in mail.service.ts; keep it in environment variables.

same as node js;directly configure.

| Attribute  | Meaning                                                     | Example                             |
| ---------- | ----------------------------------------------------------- | ----------------------------------- |
| **host**   | SMTP server address where Nodemailer connects to send email | `smtp.gmail.com`                    |
| **port**   | Network port used to connect to the SMTP server             | `587`                               |
| **secure** | Whether to use a secure TLS connection immediately          | `false` for `587`, `true` for `465` |
| **auth**   | Credentials used to authenticate with the SMTP server       | `{ user, pass }`                    |

host   → WHERE to connect
port   → WHICH port to connect to
secure → HOW to establish the secure connection
auth   → WHO is allowed to send
