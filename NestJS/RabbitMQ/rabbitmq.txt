NOW RABBITMQ
WHY DO WE NEED QUEUES?
============================================================
Suppose a user creates an account.
Without a queue:

User
 ↓
API
 ↓
Create User
 ↓
Send Email
 ↓
Generate Notification
 ↓
Response

example:
async register(data) {
  const user = await this.userService.create(data);
  await this.emailService.sendWelcomeEmail(user);
  await this.notificationService.create(user);
  return user;
}

The user has to wait for everything.
With a queue:

User
 ↓
API
 ↓
Create User
 ↓
Queue
 ↓
Response immediately


Then in background:

Queue
 ↓
Worker / Consumer
 ↓
Send Email


Benefits:

- Faster API response
- Background processing
- Decouplingg
- Better scalability
- Retry failed work
- Handle traffic spikes
- Communication between microservices
============================================================
RabbitMQ is a Message Broker.
It is commonly used for communication between services.

Example:
User Service
      ↓
   RabbitMQ
      ↓
Email Service

User Service does not directly call Email Service.
RabbitMQ sits between them.

============================================================
15. RABBITMQ EXCHANGE
============================================================
Producer normally sends a message to an Exchange.

Exchange decides which queue should receive
the message.


Producer
   ↓
Exchange
   ↓
Queue
   ↓
Consumer


Exchange types:
1. Direct
2. Fanout
3. Topic
4. Headers
============================================================
16. DIRECT EXCHANGE
============================================================
Uses an exact Routing Key.


Producer
   ↓
Direct Exchange
   ↓
routingKey = "user.created"
   ↓
user_queue

Only the appropriate binding receives it.
============================================================
17. FANOUT EXCHANGE
============================================================
Broadcasts the message to all bound queues.
Producer
     ↓
Fanout Exchange
   /    |    \
  ↓     ↓     ↓
Queue1 Queue2 Queue3

Example:
User Created

Email Service
Notification Service
Analytics Service

All receive the event.
============================================================
18. TOPIC EXCHANGE
============================================================
Uses routing-key patterns.
Examples:
user.created
user.updated
user.deleted


Binding:
user.*

matches:
user.created
user.updated
user.deleted


Another:
user.#

can match multiple levels.
============================================================
19. BINDING
============================================================
Binding connects:

Exchange
    ↓
Queue


Example:
events_exchange
      ↓
   Binding
      ↓
email_queue


with routing key:
user.created
============================================================
20. ROUTING KEY
============================================================
Routing Key tells the Exchange how to route
the message.


Example:
"user.created"

Producer:
publish(
    "user.created",
    data
)

Exchange checks the bindings.
============================================================
21. QUEUE
============================================================
Queue stores messages until consumers process them.

Exchange
   ↓
Queue
   ↓
Consumer

Example:
email_queue
============================================================
22. CONSUMER
============================================================
Consumer receives and processes messages.

RabbitMQ
   ↓
email_queue
   ↓
Email Service
   ↓
Process Message
============================================================
23. ACKNOWLEDGEMENT
===========================================================
ACK means:
"I successfully processed this message."
Flow:


RabbitMQ
   ↓
Consumer
   ↓
Process
   ↓
ACK
   ↓
RabbitMQ removes message

If the consumer crashes before ACK,
RabbitMQ can deliver the message again.
============================================================
24. NACK
============================================================
NACK means:
"I could not process this message."

Example:

Consumer
   ↓
Process
   ↓
FAIL
   ↓
NACK


Depending on configuration:
- Requeue
- Retry
- Dead Letter Queue
============================================================
25. PREFETCH
============================================================
Prefetch controls how many unacknowledged messages
a consumer can receive.
Example:

prefetch = 1
Consumer gets:

Message 1
After ACK:

Message 2

This prevents one worker from receiving too many
messages at once.
============================================================
26. DURABLE QUEUE
============================================================
A durable queue survives a RabbitMQ restart.

Example:
durable: true

Important for production systems.
============================================================
27. PERSISTENT MESSAGE
============================================================
A persistent message asks RabbitMQ to persist
the message.

Useful when message durability is important.

Remember:

Durable Queue
+
Persistent Message

helps protect messages from broker restarts.

30. @EventPattern
============================================================
Used for event-based communication.

Producer:
client.emit(
    'user.created',
    data
);


Consumer:
@EventPattern('user.created')
handleUserCreated(data) {
    console.log(data);

}


Flow:


emit()
 ↓
RabbitMQ
 ↓
@EventPattern()
============================================================
31. @MessagePattern
============================================================
Used for request-response communication.

Producer:
client.send(
    'user.get',
    userId
);


Consumer:

@MessagePattern('user.get')
getUser(id) {

    return user;

}


Flow:


send()
 ↓
RabbitMQ
 ↓
@MessagePattern()
 ↓
Response


============================================================
32. emit() vs send()
============================================================

→ Asynchronous


send()

→ Response expected


Remember:


client.emit()

client.send()
     ↓
@MessagePattern()

35. COMPETING CONSUMERS
============================================================
Multiple workers can consume from the same queue.


              Queue
           /    |    \
          ↓     ↓     ↓
       Worker1 Worker2 Worker3


RabbitMQ distributes messages among them.
This provides horizontal scaling.
============================================================
36. RETRY IN RABBITMQ
============================================================
A message may fail processing.

Message
 ↓
Consumer
 ↓
FAIL
 ↓
Retry
 ↓
Consumer
 ↓
SUCCESS

Possible strategies:
- Immediate retry
- Delayed retry
- Exponential backoff
- Dead Letter Queue
============================================================
37. DEAD LETTER QUEUE
============================================================
DLQ stores messages that cannot be processed.


Main Queue
    ↓
Consumer
    ↓
FAIL
    ↓
Retry
    ↓
FAIL
    ↓
DLQ


Useful for:

- Debugging
- Failed messages
- Manual retry
- Error investigation

============================================================
38. DEAD LETTER EXCHANGE
============================================================
RabbitMQ can route failed messages through
a Dead Letter Exchange.


Main Queue
    ↓
Failure
    ↓
DLX
    ↓
Dead Letter Queue
============================================================
39. IDEMPOTENCY
============================================================
Messages can sometimes be delivered more than once.

Example:
payment.completed

Consumer receives it twice.


If consumer blindly processes it twice:
Payment could be duplicated.


Therefore:
Check whether the event was already processed.
Example:
eventId = "abc123"

Database:
abc123 already exists?


YES
 ↓
Ignore


NO
 ↓
Process


This is called:
IDEMPOTENCY
============================================================
40. AT-LEAST-ONCE DELIVERY
============================================================
RabbitMQ systems commonly use
at-least-once delivery patterns.
Meaning:

Message should be processed,
but duplicate delivery can happen.

Therefore:


ACK
+
Idempotent Consumer


is very important.
============================================================
41. MESSAGE ORDER
============================================================
RabbitMQ can preserve queue order in simple cases.
But ordering becomes more complicated with:
- Multiple consumers
- Retries
- Requeue
- Failures

Therefore do not blindly depend on global ordering
in distributed systems.
============================================================
42. RABBITMQ RPC
============================================================
RPC means:
Remote Procedure Call.
Service A:

"Give me User 10"


RabbitMQ
    ↓

Returns User 10
Useful for request-response communication.
============================================================
43. CORRELATION ID
============================================================
Used to match a request with its response.
Request:
correlationId = abc123

Response:
correlationId = abc123

This is useful for RPC and distributed systems.
============================================================
44. TRACE ID
============================================================
Used to track one request across multiple services.
Example:


API
 ↓
Order Service
 ↓
Payment Service
 ↓
Notification Service

All logs contain:
traceId = abc123
Makes distributed debugging much easier.
============================================================
45. RABBITMQ + DATABASE PROBLEM
============================================================
Suppose:
Create Order in Database
        ↓
Publish RabbitMQ Event


What if:
Database succeeds
        ↓
RabbitMQ publish fails

Now the database contains the order,
but other services never receive the event.
This is a distributed consistency problem.
============================================================
46. OUTBOX PATTERN
============================================================
Solution:
Store the event in an Outbox table
inside the same database transaction.

Transaction:

Order
+
Outbox Event

Both succeed or fail together.


Then:
Outbox Worker
     ↓
RabbitMQ
     ↓
Other Services
This prevents losing important events.
============================================================
47. REDIS + RABBITMQ
============================================================
Redis and RabbitMQ can be used together,
but they have different primary purposes.

Redis:
- Cache
- Sessions
- OTP
- Temporary data
- Rate limiting(in nest js with guards)
- Fast key-value storage


RabbitMQ:

- Message broker
- Event-driven communication
- Microservices communication
- Reliable message delivery
- Queues
- Routing


Example:
NestJS API
   |
   +------ Redis
   |         ↓
   |       Cache
   |
   +------ RabbitMQ
             ↓
          Events
             ↓
       Microservices
============================================================

============================================================

1. Create Order

3. Cache frequently used data in Redis
4. Publish order.created to RabbitMQ


Flow:

Order API
   ↓
MySQL
   ↓
Redis
   ↓
RabbitMQ
   ↓

   ↓

Redis is NOT replacing RabbitMQ.
RabbitMQ is NOT replacing Redis.

49. RABBITMQ vs BULLMQ
============================================================
RabbitMQ:
Main purpose:
Message Broker / Microservice Communication


Good for:

- Microservices
- Events
- Service-to-service communication
- Routing
- Pub/Sub
- Request-response


BullMQ:

Main purpose:
Background Job Queue


Uses:
Redis


Good for:

- Background jobs
- Delayed jobs
- Scheduled jobs
- Retry
- Job processing
