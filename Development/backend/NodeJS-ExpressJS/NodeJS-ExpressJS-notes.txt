## 🌟 What is Node.js?
🟢 **Node.js** is an **Open-Source** and **Cross-Platform JavaScript Runtime Environment** that allows JavaScript to run outside the browser.
💡 Before Node.js:
* JavaScript worked mainly inside browsers.

💡 After Node.js:
* JavaScript can be used for:

  * Backend Development
  * APIs
  * Real-Time Applications
  * Servers
  * Full Stack Development
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
## ⚡ Simple Definition
```text
Node.js = JavaScript Runtime + V8 Engine + System APIs
```

## 🔥 Why Node.js is Popular?

✅ Fast Execution using Google V8 Engine
✅ Non-Blocking Architecture
✅ Event-Driven
✅ Handles Multiple Requests Efficiently
✅ Perfect for Real-Time Applications
✅ Same Language for Frontend + Backend

## 🧠 Features of Node.js
### 1️⃣ Asynchronous & Non-Blocking
Node.js does not wait for one task to finish before starting another.

```javascript
console.log("Start");

setTimeout(()=>{
   console.log("Hello");
},2000);

console.log("End");```
📌 Output:
```javascript
Start
End
Hello
```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
### 2️⃣ Single Threaded

* Uses one main thread
* Uses Event Loop internally
* Efficiently handles many users

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

### 3️⃣ Event Driven
Node.js works on events.
Examples:

* User Request
* File Open
* Database Response
* User Login

It continuously checks:

->framework vs Library
Library:
A library is a collection of reusable functions or codes that developers call when needed.

Framework:
A framework provides a predefined structure and controls the application flow while developers write code inside it.

| Feature              | Library                    | Framework                   |
| -------------------- | -------------------------- | --------------------------- |
| Control              | You control the flow       | Framework controls the flow |
| Usage                | Call functions when needed | Framework calls your code   |
| Flexibility          | More flexible              | More structured             |
| Purpose              | Solve specific tasks       | Build complete applications |
| Inversion of Control | ❌ No                       | ✅ Yes                       |
| Size                 | Usually smaller            | Usually larger              |

🌟 What is Express.js?

Express.js is a fast, minimal, and flexible web framework for Node.js.

It is mainly used for:
✅ Backend Development
✅ Building APIs
✅ Creating Servers
✅ Handling Routes
✅ Web Applications

👉 Express.js simplifies Node.js server development.
Official Website:
https://expressjs.com

Express.js = Framework built on top of Node.js

🔥 Why Express.js?
Using only Node.js HTTP module:

const http = require('http');

const server = http.createServer((req,res)=>{
   res.end("Hello");
});
server.listen(3000);

Using only Node.js HTTP module:
❌ More code
❌ Difficult routing
❌ Hard project management

Express.js provides:
✅ Easy Routing
✅ Middleware
✅ Faster Development
✅ Better Structure
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ Fast Performance
✅ Lightweight
✅ Middleware Support
✅ REST API Development
✅ Routing System
✅ Scalable Applications
✅ Easy Integration with MongoDB

EXPRESS.JS MIDDLEWARE NOTES (BASIC TO ADVANCED)

. What is Middleware?
Middleware is a function that executes between request and response cycle.
Client Request → Middleware → Route Handler → Response
When a client sends a request to a server by visiting a URL like /users,
the request first reaches the Express application. Before the request goes
to the final route handler, it passes through middleware functions. Middleware
acts like a checkpoint where tasks such as logging, authentication, parsing
JSON data, checking permissions, or handling errors can be performed. 
After the middleware finishes its work, it calls next() to pass control
to the next middleware or the route handler(callback(controller)). Then the route handler
processes the request, performs the required logic such as fetching 
data from a database or creating a response, and finally sends a response
back to the client using methods like res.send() or res.json(). 
So the complete flow is: Client Request → Middleware → Route Handler → Response.

Middleware can:

Access request object (req)
Access response object (res)
End request-response cycle
Call next middleware using next()


# Syntax of Middleware
function middleware(req, res, next) {
    console.log("Middleware executed");
    next();
}

# Basic Example
import express from 'express';
const app = express();

function logger(req,res,next)=>{
     console.log("Hello from middleware")
     const d=new Date()
     console.log(`${req.method} ${req.url}`)
     console.log(`${d.getDate()} ${d.getMonth()}`)    
     next()
 }

app.use(logger);

app.get('/', (req, res) => {
    res.send("Home Page");
});
app.get('/about', (req, res) => {
    res.send("about Page");
});

#. Best Practices

✅ Keep middleware small
✅ Use separate files
✅ Always handle errors
✅ Use next() properly
✅ Use async try-catch

Express error-handling middleware can handle async errors,
 but there is an important condition.

❌ This does NOT work automatically in Express 4
app.get("/", async (req, res) => {
    let user = await User.findById("wrongId");
    res.send(user);
});

If an error happens here, Express 4 may not send it to the error middleware automatically.

✅ Correct way: use next(err)
app.get("/", async (req, res, next) => {
    try {
        let user = await User.findById("wrongId");
        res.send(user);
    } catch (err) {
        next(err);
    }
});

Then:

app.use((err, req, res, next) => {
    res.status(500).send(err.message);
});

Now async errors are handled correctly.


Better Solution → Wrapper Function

Instead of writing try...catch everywhere:

const wrapAsync = (fn) => {
    return function(req, res, next) {
        fn(req, res, next).catch(next);
    };
};

Usage:

app.get("/", wrapAsync(async (req, res) => {
    let user = await User.findById("wrongId");
    res.send(user);
}));

If error occurs:

.catch(next) sends error
error middleware handles it
Important
Express 5

In Express 5, async errors are handled automatically.

app.get("/", async (req, res) => {
    throw new Error("Error");
});

This automatically goes to error middleware.
But most projects still use Express 4, so wrappers are common.

🚀 WHY USE MULTER IN EXPRESS.JS
━━━━━━━━━━━━━━━━━━
🌟 Problem without multer

Express cannot handle:
❌ file uploads (images, pdf, videos)
If user sends file via form:

<form enctype="multipart/form-data">

👉 req.body will NOT contain file
👉 Express cannot read file data directly

━━━━━━━━━━━━━━━━━━
🌟 Why multer is used?

Multer is middleware for:
✔ Handling file uploads
✔ Storing files on server
✔ Accessing file data in req.file / req.files
res.file and res.files are provided by multer middleware

━━━━━━━━━━━━━━━━━━
🧠 Simple Meaning
Multer = file upload manager for Express

━━━━━━━━━━━━━━━━━━
🌟 What it gives us

After upload:

req.file   → single file  
req.files  → multiple files  

━━━━━━━━━━━━━━━━━━
🌟 Example use cases

✔ Profile image upload
✔ Resume upload
✔ Product images (e-commerce)
✔ Document upload

━━━━━━━━━━━━━━━━━━
🎯 FINAL UNDERSTANDING

❌ Without multer → Express cannot handle files  
✔ With multer → Express can receive + store uploaded files easily

   }

});

🌟 What is diskStorage?

multer.diskStorage()
→ Defines HOW and WHERE uploaded files are saved on disk (server folder).

🌟 It has 2 MAIN parts

1️⃣ destination()
2️⃣ filename()

🌟 1. destination()
destination: function (req, file, cb)
👉 Decides WHERE file will be stored

🌟  req
req → request object

🌟  file
file → uploaded file object
👉 Contains file info like:

{
  fieldname,
  originalname,
  mimetype,
  size,
  filename,
  path
}


🧠 Example:
file.originalname → "photo.png"
file.mimetype → "image/png"



🌟  cb (callback)

cb → callback function

👉 used to tell multer:
✔ where to save file(in destination)
✔ what name to give file(in fileName)
✔ success or error


🧠 Syntax
cb(error, value)

🧠 Example(in destination)
cb(null, '/uploads')

👉 Meaning:
Save file inside "uploads" folder

✔ null → NO error
✔ '/uploads' → success value (folder name)

📌 Important

✔ 'uploads/' must exist
✔ otherwise error occurs

✔ If NO error:
   error = null

❌ If error:
   error = new Error("message")

🧠 Example with error
cb(new Error("Invalid file"), null)


🌟 2. filename()
filename: function (req, file, cb)
👉 Decides WHAT will be the file name

🧠 Example
cb(null, Date.now() + '-' + file.originalname)


📌 Meaning
✔ Date.now() → unique number (avoid duplicate names)
✔ file.originalname → real uploaded file name
🌟 Final filename example
1700000000-photo.png

or
cb(null,Date.now()+path.extfile(file))//this will extract extention

🌟 Why we use custom filename?

✔ Avoid duplicate file names
✔ Prevent overwrite of files
✔ Keep files unique

Multer receives files
        ↓
FOR EACH file:
   1. fileFilter runs
   2. destination runs
   3. filename runs
        ↓
file is saved

🌟 STEP-BY-STEP FLOW

1️⃣ Request comes with files
        ↓
2️⃣ Multer reads stream (multipart/form-data)
        ↓
3️⃣ Each file is processed one by one:
        - fileFilter runs
        - destination runs
        - filename runs
        - file is saved to disk
        ↓
4️⃣ AFTER saving each file:
        ↓
5️⃣ Multer creates a FILE OBJECT
        ↓
6️⃣ That object is PUSHED into req.files

🌟 TYPES OF MULTER ERRORS

Multer errors come from:
👉 multer.MulterError

error.code of multer.MulterError
━━━━━━━━━━━━━━━━━━
🌟 1. LIMIT_FILE_SIZE

Occurs when:
✔ File size exceeds limit

limits: { fileSize: 1MB }
User uploads 3MB file

━━━━━━━━━━━━━━━━━━
🌟 2. LIMIT_FILE_COUNT

Occurs when:
✔ Too many files uploaded

upload.array('files', 5)
User sends 10 files

━━━━━━━━━━━━━━━━━━
🌟 3. LIMIT_UNEXPECTED_FILE

Occurs when:
✔ Wrong field name used

Example:
upload.single('userfile')
User sends 'profilepic'

━━━━━━━━━━━━━━━━━━
🌟 4. LIMIT_PART_COUNT

Occurs when:
✔ Too many parts in multipart form

━━━━━━━━━━━━━━━━━━
🌟 5. LIMIT_FIELD_KEY / LIMIT_FIELD_VALUE

Occurs when:
✔ Field name/value too large

━━━━━━━━━━━━━━━━━━
🌟 HOW TO CHECK ERROR

if (error instanceof multer.MulterError) {
   console.log(error.code);
}





 LIMIT_UNEXPECTED_FILE

🌟 Meaning

This error occurs when:
👉 You send file with WRONG field name
👉 OR field name not matching multer config

🧠 Example

upload.array('userdocuments', 5)

But frontend sends:
name="profilepic"

━━━━━━━━━━━━━━━━━━
❌ Result
Error: LIMIT_UNEXPECTED_FILE

━━━━━━━━━━━━━━━━━━
🌟 Why it happens?

✔ Multer expects specific field name
✔ Other field names are considered invalid

━━━━━━━━━━━━━━━━━━
🌟 Fix

✔ Use correct field name
✔ OR use upload.any() / upload.fields()

--> Authentication Using session bcryptjs
bcryptjs Notes

What is bcryptjs?

bcryptjs is a library used to hash passwords
 and compare passwords securely.

It is mainly used in:

* Authentication
* Login systems

Install:
npm install bcryptjs
Import:
import bcrypt from 'bcryptjs'

Why We Use bcryptjs
Never store original passwords in database.
Wrong:
password: "naeem123"
Correct:
password: "$2b$10$abc..."
bcrypt converts password into a hashed string.

Hashing Password
Syntax:
bcrypt.hash(password,saltRounds)

Example:

const hashedPassword = await bcrypt.hash(
userpassword,
10
)

* password → original password
* 10 → salt rounds
---
Salt Rounds
Salt rounds decide:

* security
* hashing speed

5  → Fast → Low Security
10 → Normal → Good Security
12+ → Slow → High Security

Usually:
bcrypt.hash(password,10)

---

Registration Example
app.post('/register', async (req,res)=>{
const {username,userpassword} = req.body
const hashedPassword = await bcrypt.hash(
userpassword,
10
)
await User.create({
username,
userpassword: hashedPassword
})

res.send("Registered Successfully")
})



Compare Password
Used during login.
Syntax:
bcrypt.compare(
enteredPassword,
hashedPassword
)

Returns:
* true
* false

---

Login Example

app.post('/login', async (req,res)=>{
const {username,userpassword} = req.body
const user = await User.findOne({username})
if(!user){
return res.send("User not found")
}
const isMatch = await bcrypt.compare(
userpassword,
user.userpassword
)
if(!isMatch){
return res.send("Invalid Password")
}

res.send("Login Successful")
})

---
Important Rule
Wrong:
if(userpassword === user.userpassword)

Correct:
bcrypt.compare()

Because hashed password is different from original password.
---

Async Await
bcrypt operations take time because hashing is heavy.

Use:
await bcrypt.hash()

and
await bcrypt.compare()

---

bcrypt.hash()
Converts plain password into a hashed (encrypted) password.
bcrypt.compare()
Compares plain password with hashed password and returns true/false.
bcrypt.genSalt()
Generates a salt value used to strengthen password hashing.
bcrypt.hashSync()
Synchronous version of hash() used to hash password without async.
bcrypt.compareSync()
Synchronous version of compare() used for password checking without async.

-->Common Errors

1. Illegal arguments: string, undefined

Reason:

* user.userpassword is undefined
Fix:

* Check schema field names
* Check MongoDB values

---

2. Loading Forever

Reason:
* No response sent
Fix:

res.send()
or
res.redirect()
---

3. Password Not Stored
Reason:
* Schema missing password field
Fix:
userpassword:String
---
Encryption vs Hashing

Encryption:

* Can decrypt
* Two-way
* Used for data

Hashing:

* Cannot decrypt
* One-way
* Used for passwords

bcrypt uses hashing.

---

Authentication Flow

Register:

1. User enters password
2. Password hashed
3. Hash stored in database

Login:

1. User enters password
2. Stored hash retrieved
3. bcrypt.compare() checks password
4. Login success/fail

🌟 SIGNED COOKIE (Express)

✔ Signed cookie = cookie with a secret signature to prevent tampering

🌟 SET SIGNED COOKIE
app.use(cookieParser("mysecretkey"))

res.cookie("username", "Naeem", {
   signed: true
})

👉 secret is required for signing


🌟 HOW IT LOOKS
Cookie stored in browser:

username=s:Naeem.signatureHash


🌟 READ SIGNED COOKIE
req.signedCookies.username
✔ verified cookie value

❌ signature becomes invalid
✔ req.signedCookies returns undefined


✔ signed cookie = secure cookie with signature
✔ prevents user from modifying cookie data

◆ WHY CSRF HAPPENS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Browser automatically sends:

✔ Cookies
✔ Session IDs
✔ Authentication cookies

When a user logs into a website, the server sends a cookie to the browser.
Example:
Set-Cookie: sessionId=abc123

The browser stores it automatically.
Later, whenever the user sends requests to that website, the browser automatically 
attaches the cookie.

Example:
POST /transfer-money
Cookie: sessionId=abc123

The server checks:
sessionId=abc123

and thinks:
"This request is from the real logged-in user."
But the request may actually come from a malicious website.
That is why CSRF is dangerous.
The browser automatically sends cookies without checking whether the request came from:

✔ Real website
❌ Fake attacker website

So the server may trust a fake request.
with every request.
Attackers exploit this automatic behavior.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CSRF protection ensures that requests come from:

✔ Your real frontend
❌ Not malicious websites

--->CORS
========================
CORS (Cross-Origin Resource Sharing)
========================

Definition:
CORS is a browser security feature that allows or restricts
requests between different origins using HTTP headers.
----------------------------------------
What is an Origin?
----------------------------------------

Origin = Protocol + Domain + Port

Example:
http://localhost:3000
https://google.com

Different port/domain/protocol = Different Origin
----------------------------------------
Why do we need CORS?
----------------------------------------

Browsers follow the Same-Origin Policy for security.

Without CORS, any website could access another website’s API
using the user’s login session.

So browsers block cross-origin requests unless the server
gives permission.

----------------------------------------
Example
----------------------------------------

Frontend:
http://localhost:3000

Backend:
http://localhost:5000

Frontend request:

fetch("http://localhost:5000/users")

Browser checks:
3000 != 5000

Different origin detected.

Result:
Request blocked unless backend allows it using CORS.

----------------------------------------
Why is CORS needed even with Express?
----------------------------------------

Express only creates backend routes.

Example:

app.get("/users", ...)

But Express does NOT automatically allow cross-origin requests.
Browser requires special headers like:
Access-Control-Allow-Origin

So we use CORS middleware.

----------------------------------------
Install CORS
----------------------------------------

npm install cors

----------------------------------------
Use CORS in Express
----------------------------------------

import cors from "cors";

app.use(cors());
This allows all origins.
//same as above
 app.use(cors());
  //same
//   app.use(
//   cors({
//     origin: "*",
//   }),
// );

----------------------------------------
Allow Specific Frontend
----------------------------------------

app.use(cors({
    origin: "http://localhost:3000"
    //origin:[origin1,origin2]
}));

Only this frontend can access the backend.

----------------------------------------
Important Point
----------------------------------------
there is still a lot to learn in cors (later)

CORS is enforced by the browser, not by Express or Node.js.
Postman, Thunder Client, and curl do not check CORS.

----------------------------------------
Flow of CORS
----------------------------------------

Frontend Request
       ↓
Browser checks origin
       ↓
Different origin?
       ↓
Yes
       ↓
Browser asks server for permission
       ↓
Server sends CORS headers
       ↓
Allowed or Blocked

----------------------------------------
Common Error
----------------------------------------

Access to fetch at
'http://localhost:5000'
from origin
'http://localhost:3000'
has been blocked by CORS policy.

----------------------------------------
Interview Definition
----------------------------------------

CORS (Cross-Origin Resource Sharing) is a browser security
mechanism that allows or restricts web applications from
accessing resources from different origins using HTTP headers.

==================== JWT IN NODE.JS ====================
JWT (JSON Web Token) is used for authentication and 
authorization in Node.js apps (especially with Express).
 It helps you verify users without storing session data on
  the server.

🔐 JWT (JSON Web Token)

- Used for Authentication & Authorization
- Stateless (no session stored on server)
- Used in login systems (MERN, REST APIs)

--------------------------------------------------------
📦 INSTALL
--------------------------------------------------------
npm install jsonwebtoken

--------------------------------------------------------
🧠 HOW JWT WORKS
--------------------------------------------------------
1. User logs in
2. Server creates JWT token
3. Token sent to client
4. Client stores token (localStorage / cookie)
5. Client sends token in request headers
6. Server verifies token

🌟 JWT STRUCTURE WITH EXAMPLE

TOKEN(JWT) FORMAT:
HEADER.PAYLOAD.SIGNATURE

Example token:
abc123.def456.xyz789

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🌟 1. HEADER (Algorithm Info)
Example:
{
   "alg": "HS256",
   "typ": "JWT"
}

✔ Tells which algorithm is used
✔ Always encoded (Base64)
✔ You DON’T manually set "alg" in most cases
✔ jsonwebtoken package sets it automatically


🌟 2. PAYLOAD (User Data)

Example:
{
   "id": 101,
   "username": "Naeem",
   "role": "user"
}

✔ Contains actual data
✔ NOT encrypted (only encoded)
take small payload for jwt id username is enought


🌟 3. SIGNATURE (Security Check)

Created using(auto):
HMACSHA256(
   base64(header) + "." + base64(payload),
   "secretKey"
)

Example:
xyz789signature

✔ Used to verify token is not modified
🌟 FULL EXAMPLE TOKEN

HEADER:
{"alg":"HS256","typ":"JWT"}

PAYLOAD:
{"id":101,"username":"Naeem"}

SIGNATURE:
securehash123

FINAL TOKEN:

abc123.def456.securehash123

🎯 FINAL SUMMARY

✔ Header = algorithm type
✔ Payload = user data
✔ Signature = security verification using secret key

🛡️ MIDDLEWARE (VERIFY TOKEN)
--------------------------------------------------------
import jwt from "jsonwebtoken";

const verifyToken = (req, res, next) => {
  const authHeader = req.headers.authorization;

  // 1. check header exists
  if (!authHeader) {
    return res.status(401).send("Access denied: No token provided");
  }

  // 2. extract token from "Bearer <token>"
  const token = authHeader.split(" ")[1];

  if (!token) {
    return res.status(401).send("Access denied: Invalid token format");
  }

  try {
    // 3. verify token
    const decoded = jwt.verify(token, "secretKey");
   // It returns the payload that was originally stored inside the token with iat,exp .

    // 4. attach user data to request
    req.user = decoded;

    next();
  } catch (err) {
    return res.status(400).send("Invalid token");
  }
};
how works?
1️⃣ Take token
2️⃣ Split into 3 parts
3️⃣ Recreate signature using secretKey
4️⃣ Compare with token signature

✔ If token is valid → returns decoded data(payload)
❌ If token is invalid → throws ERROR


It only:
✔ checks token is valid
✔ checks signature
✔ checks expiry
✔ returns payload

✔ req.user = decoded means:

   “store authenticated user data
    in request object for future use”
🌟 DIFFERENCE

┌──────────────────┬──────────────────────┐
│ Payload          │ Decoded data         │
├──────────────────┼──────────────────────┤
│ Your data only   │ Payload + metadata   │
│ id, username     │ + iat, exp           │
└──────────────────┴──────────────────────┘


🌟 EXTRA FIELDS

✔ iat = issued at time
 Means: token created time
 Automatically added by JWT
✔ exp = expiry time (if expiresIN is set)
 Means: token expiration time
 After this token becomes invalid

JS thinks 66cfa12b... is a variable name, not data, so it throws ReferenceError.
When you wrap it in quotes, it becomes a proper string → safe to use.
Example: onclick="viewStudent('66cfa12b9a8e7d4f3c9a1234')" (correct)
Without quotes → variable lookup ❌ | With quotes → string value ✅
Best practice: avoid inline onclick, use
button.addEventListener("click", () => viewStudent(student._id)) 👍

-->🌈Rate Limiting in Node.js (Express)
Rate limiting means controlling how many 
requests a user can send to your API in a specific time.
Example:

100 requests per 15 minutes
If exceeded → block user temporarily

Used for:

Preventing brute-force attacks
Preventing spam
Avoiding server overload
API abuse protection

Package:
npm install express-rate-limit
or
npm install express-slow-rate (this can be used it is seprate package)

setup:
import express from 'express'
import rateLimit from 'express-rate-limit'

const app = express()

const limiter = rateLimit({
    windowMs: 15 * 60 * 1000, // 15 minutes
    max: 100, // limit each IP to 100 requests
    message: "Too many requests, try again later"
})

app.use(limiter)//for all route this will apply we can make differnt rateLimit for different route alos

app.get('/', (req,res)=>{
    res.send("API Working")
})

app.listen(3000)

->express-rate-limit remembers the same user mainly 
using the IP address.

Request comes
      ↓
Get IP address
      ↓
Check stored count for that IP
      ↓
Increase count
      ↓
If count > max
      ↓
Block request

Important Options
1. windowMs

Time duration.
windowMs: 15 * 60 * 1000
= 15 minutes

2. max
Maximum requests allowed.
max: 100

After 100 requests → blocked.

3. message
Custom response message.
message: "Too many requests"

4. statusCode
Custom status code.

statusCode: 429
429 = Too Many Requests

5. standardHeaders
Returns rate limit info in headers.

standardHeaders: true

Headers:

RateLimit-Limit
RateLimit-Remaining
RateLimit-Reset

6. Skip Successful Requests

Useful for login APIs.

const limiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    max: 5,
    skipSuccessfulRequests: true
   // Only failed requests counted.
})

7.const limiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    max: 5,
    handler: (req,res)=>{
        res.status(429).json({
            success:false,
            message:"Too many requests"
        })
    }
})
//return what res we want to send

🌈 helmet in Express.js
helmet is a middleware package in Node.js/Express used to
 improve API and web application security by setting 
 various HTTP security headers automatically.

Package
npm install helmet
Import and Use

import helmet from "helmet"
import express from "express"
const app = express()
app.use(helmet())

When a browser communicates with your server, headers are sent in the response.
helmet adds security-related headers to protect against common attacks like:
.XSS (Cross-Site Scripting)
.Clickjacking
.MIME sniffing
.Data injection attacks
.Information leakage

What helmet Does Internally:
helmet() enables multiple security middlewares together.
| Security Header             | Purpose                       |
| --------------------------- | ----------------------------- |
| `X-Content-Type-Options`    | Stops MIME type sniffing      |
| `X-Frame-Options`           | Prevents clickjacking         |
| `Content-Security-Policy`   | Reduces XSS attacks           |
| `Strict-Transport-Security` | Forces HTTPS                  |
| `Referrer-Policy`           | Controls referrer information |
and more

service → Predefined SMTP shortcut that automatically configures host, port, and security for providers like Gmail/Outlook so you don’t manually set SMTP details

host → The actual SMTP server address (e.g. smtp.gmail.com) that routes your email through the provider’s mail delivery system

port → Network entry point for SMTP connection where 587 is used for TLS (STARTTLS) and 465 is used for SSL encrypted direct connection

secure → Boolean flag that decides encryption type; true means SSL (required password) from start, false means connection starts plain and upgrades to TLS

auth → Authentication object that verifies sender identity with the SMTP server before allowing any email transmission

user → Email address used as login username and sender identity in SMTP communication (MAIL FROM and AUTH step)

pass → Secret credential (usually App Password in Gmail) used to authenticate SMTP login securely instead of normal password

tls → Advanced security settings that control encryption behavior, certificate validation, and secure channel rules during SMTP handshake

requireTLS → Forces the SMTP connection to use TLS encryption strictly; if TLS fails, email sending is aborted for security

debug → Enables detailed step-by-step logs of SMTP connection, authentication, and email sending process for troubleshooting

logger → Prints internal Nodemailer communication logs in console to track SMTP events and responses from server

transporter → Core Nodemailer engine object that holds SMTP configuration and executes email sending via sendMail()

sendMail() → Main function that runs full email lifecycle: connect to SMTP → authenticate → create message → send → receive server response

mailOptions → Object that defines email content including sender, receiver, subject, body, and attachments

from → Sender address shown in email header and used internally in SMTP MAIL FROM command

to → Recipient email address where the email will be delivered

subject → Email title shown in inbox preview line

text → Plain text version of email content without formatting

html → HTML formatted email content that supports styling, links, and structure

attachments → Array used to send files like PDFs, images, and documents along with email message

SMTP → Protocol (rules system) used for sending emails between client and mail server using commands like AUTH, MAIL FROM, RCPT TO, DATA

TLS → Encryption protocol that secures email data during transmission between client and server

SSL → Older encryption method that establishes a fully secure connection before any SMTP communication begins

userSchema.pre('save', async function(next){
   if(this.isModified('password')){
      this.password = await bcrypt.hash(this.password,12)
   }

   next()

})

🔹 WHAT IS pre('save') ?

✔ Mongoose middleware / hook
✔ Runs BEFORE document is saved in MongoDB

FLOW:

user.save()
      ↓
pre('save') runs
      ↓
password hashed
      ↓
document saved

🔹 WHAT DOES this MEAN?

✔ this = current document being saved
Example:

{
   username:"Naeem",
   password:"12345"
}

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔹 this.isModified('password')

✔ checks whether password field changed or not

WHY IMPORTANT?

Without this:
❌ password hashes again and again

Example:

12345
 ↓
hashedPassword

save again
 ↓
hash(hashedPassword)

❌ login fails

🔹 bcrypt.hash(this.password,12)

✔ hashes password securely

12 = salt rounds

Higher rounds:
✔ more secure
❌ slower

Common values:
10–12

✔ continues save operation

Without next():
❌ request may hang

# 🎯 express-ejs-layouts in Node.js (Detailed Notes)

express-ejs-layouts` is a middleware used with `Express.js`
and `EJS` to create a common layout/template for multiple pages.

Instead of repeating navbar, footer, header, CSS links in
every EJS file, we create one main layout file.

# ❓ Why We Use It

Without layouts:

```ejs
<!-- home.ejs -->
<html>
<head>...</head>
<body>
  <nav>...</nav>

  <h1>Home Page</h1>

  <footer>...</footer>
</body>
</html>
```

```ejs
<!-- about.ejs -->
<html>
<head>...</head>
<body>
  <nav>...</nav>

  <h1>About Page</h1>

  <footer>...</footer>
</body>
</html>
```

# ❌ Problem
➡️ Repeated code
➡️ Hard to manage
➡️ Editing navbar/footer everywhere is difficult

# ✅ Solution → `express-ejs-layouts`
We create:
layout.ejs

and all pages load inside it.

# 📦 Installation

npm install express-ejs-layouts

# 📁 Folder Structure

project/
│
├── views/
│   ├── layout.ejs
│   ├── home.ejs
│   └── about.ejs
│
├── public/
├── app.js
```

# res.locals in Express.js

`res.locals` is an object in Express.js used to store data that is available only during the current request-response cycle.
It is mainly used to send common data from middleware to EJS views.

---

# Syntax

```js
res.locals.key = value;
```

Example:

```js
res.locals.username = "Naeem";
```

Now this variable can be accessed directly inside EJS:

```ejs
<%= username %>
```

---

# Why We Use res.locals

Instead of sending the same data repeatedly in every route:

```js
res.render('home', {
    categories,
    latestNews,
    settings
});
```

we can store the data once using `res.locals`:

```js
res.locals.categories = categories;
res.locals.latestNews = latestNews;
res.locals.settings = settings;
```

Now all EJS files can access these variables directly.

---

# Your Example

```js
res.locals.settings = settings;
res.locals.latestNews = latestNews;
res.locals.categories = categories;
```

This means:

| Variable   | Available in EJS As |
| ---------- | ------------------- |
| settings   | `<%= settings %>`   |
| latestNews | `<%= latestNews %>` |
| categories | `<%= categories %>` |

---

# Flow of res.locals

## Middleware

```js
const loadData = (req, res, next) => {

    res.locals.siteName = "News CMS";

    next();
};
```

↓

## Route

```js
app.get('/', loadData, (req, res) => {
    res.render('index');
});
```

↓

## EJS

```ejs
<h1><%= siteName %></h1>
```

Output:

```html
<h1>News CMS</h1>
```

---

# Important Points

## 1. Request Specific

`res.locals` exists only for one request.

After the response finishes, the data is automatically removed.

---

## 2. Common Uses

`res.locals` is mostly used for:

* Logged-in user
* Categories
* Navbar data
* Website settings
* Recent posts
* Notifications
* Flash messages

---

# Difference Between app.locals and res.locals

| Feature  | app.locals         | res.locals           |
| -------- | ------------------ | -------------------- |
| Scope    | Entire application | Single request       |
| Lifetime | Permanent          | Temporary            |
| Used For | Global constants   | Dynamic request data |

import News from "../models/news.js";
import User from "../models/user.js";
import Setting from "../models/setting.js";

const cache = new NodeCache();

const loadCommonData = async (req, res, next) => {

    try {

        let latestNews = cache.get('latestNewsCache');
        let categories = cache.get('categoriesCache');
        let settings = cache.get('settingsCache');

        if (!latestNews || !categories || !settings) {
            settings = await Setting.findOne().lean();
            latestNews = await News.find()
                .sort({ date: -1 })
                .limit(5)
                .populate('category', 'name slug')
                .populate('author', 'fullname')
                .lean();

            const categoriesInUse =
                await News.distinct('category');

            categories = await Category.find({
                _id: { $in: categoriesInUse }
            }).lean();


            // Cache Data
            cache.set('latestNewsCache', latestNews, 3600);
            cache.set('categoriesCache', categories, 3600);
            cache.set('settingsCache', settings, 3600);
        }


        // Global Variables for Views

        res.locals.settings = settings;
        res.locals.latestNews = latestNews;
        res.locals.categories = categories;
        next();

    }
    catch (err) {

        console.error(err);

        next(err);
    }
};

export default loadCommonData;

const app=express()
const server = http.createServer(app);
This line creates a real HTTP server using Node.js.

Simple Meaning
Express app  → only handles routes/middleware
HTTP server → actually listens to browser requests

So this line connects Express to a real web server.

Internally
http.createServer(app)

means:

"Use Express app to handle all incoming requests"
What Happens Step-by-Step
1. Browser sends request

Example:

http://localhost:3000
2. HTTP server receives request

The server created by:

const server = http.createServer(app);
accepts the request.

3. Request goes to Express

Express checks:

Routes
Middleware
Static files

Example:

app.get('/', ...)
Visual Flow
Browser
   ↓
HTTP Server
   ↓
Express App
   ↓
Response
Why Needed?

Because Express itself is NOT the actual web server.

Express is just a framework built on top of Node.js HTTP module.
The real server is created by:

http.createServer()



Example Without Express
Pure Node.js server:

import http from 'http';
const server = http.createServer((req, res) => {
    res.end('Hello');
});
server.listen(3000);

Here:
req = request
res = response


Example With Express

const app = express();
const server = http.createServer(app);
Now Express handles requests instead of manually writing everything.
Why Important for Socket.IO?

Socket.IO needs direct access to the HTTP server.

So:

const io = new Server(server);
attaches Socket.IO to that HTTP server.

If You Use Only app.listen()
app.listen(3000);

Express secretly creates an HTTP server internally.
But you cannot properly share/control it for Socket.IO.
So we manually create the server.

Real-Life Analogy
Express = Manager
HTTP Server = Building
Socket.IO = Live communication room

Socket.IO needs access to the whole building, not just the manager.

Short Notes
http.createServer(app)
Purpose:
Creates actual web server
Uses Express to handle requests
Allows Socket.IO integration
One-Line Definition
http.createServer(app) creates a Node.js HTTP server and uses the Express app to process incoming requests.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Like this:

✔ Actual server object

you don't have server variable.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📌 COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ ONLY EXPRESS

✔ Easy
✔ Good for normal websites/APIs

📌 WHAT IS WEBSOCKET ?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🌐 WebSocket is a communication protocol
used for REAL-TIME communication between:

🖥️ Client (Browser)
        ↕
🌍 Server

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📌 NORMAL HTTP CONNECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

❌ HTTP is request-response based.

Flow:

Browser Request
       ↓
Server Response
       ↓
Connection Closed

📌 Problem:
Server cannot send data automatically.

Example:
❌ Chat app
❌ Live score
❌ Notifications

Need repeated requests.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📌 WEBSOCKET CONNECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ WebSocket keeps connection OPEN.

Flow:

Browser ↔ Server
      ↕
Continuous Connection

📌 Both can send data anytime.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📌 FEATURES OF WEBSOCKET
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✔ Full Duplex Communication
→ Both send/receive simultaneously
✔ Persistent Connection
→ Connection stays alive
✔ Real-Time Communication
✔ Faster than repeated HTTP requests

✔ Low latency

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📌 WEBSOCKET FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1️⃣ Browser sends HTTP request
2️⃣ Upgrade request happens

HTTP
   ↓
WebSocket

3️⃣ Persistent connection established
4️⃣ Real-time data transfer starts

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

📌 WHAT IS SOCKET.IO ?

🚀 Socket.IO is a JavaScript library
built ON TOP OF WebSocket.

It makes real-time communication easier.
