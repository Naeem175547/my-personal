--->🎨 Styling in React

In React, there are three common ways to apply styling:

🔹 1. Inline CSS

In React, inline styles are applied using a JavaScript object instead of a string.

function App() {
  const myStyle = {
    color: "white",
    backgroundColor: "black",
    padding: "10px",
    textAlign: "center"
  };

  return <h1 style={myStyle}>Styled Text</h1>;
}

✨ Key Points:

🧩 Styles are written as a JavaScript object
🔤 CSS properties use camelCase (backgroundColor)
❌ Hyphen (-) is not used
🌐 2. External CSS

You can write CSS in a separate file and import it into your component.

import "./App.css";

function App() {
  return <h1 className="title">Hello World</h1>;
}

✨ Key Points:

⚠️ Use className instead of class
🆔 id remains the same
🌍 Styles are global (can affect other components)
🧩 3. CSS Modules

CSS Modules help avoid global CSS conflicts by scoping styles to a specific component.

📌 Definition

👉 CSS Module = Locally scoped CSS
👉 No class name conflicts between components

🛠️ Steps to Use CSS Modules

1️⃣ Create a CSS Module file

App.module.css
.title {
  color: green;
  font-size: 30px;
}

2️⃣ Import the module

import styles from "./App.module.css";

3️⃣ Apply the class

function App() {
  return <h1 className={styles.title}>Hello React</h1>;
}
🏷️ Naming Convention

👉 File name does NOT have to match the component
👉 But it is a best practice ✅

✔️ Valid names:

style.module.css
main.module.css
App.module.css
⭐ Why Matching Names is Recommended

Using same name (e.g., App.js → App.module.css) helps:

📖 Better readability
🧹 Easy maintenance
👉 You can use any variable name while importing CSS Module
👉 It is an object 
🔍 Quick identification of styles
Priority:👉 Inline CSS > CSS Module = External CSS(both useus className) but css module wins  race beacuse of local scope
in css:👉 !important > Inline > ID > Class > Element

--->>🧠 What is State?
👉 State is a built-in object in React that stores data or information about a component,
 and when it changes, the component re-renders (updates the UI).

👉 State = data that changes over time in a component

🔹 How to create State(use useState hook that let us allow to use state)
const [count, setCount] = useState(0);
count → current value
setCount → function to update it
🔹 Key Rules

1️⃣ State is dynamic

Changes → UI automatically updates

2️⃣ Never update state directly ❌

count = count + 1   // ❌ wrong

✅ Always use setter:

setCount(count + 1)

3️⃣ State updates are asynchronous
👉 Value doesn’t update immediately

4️⃣ Use previous state when needed

setCount(prev => prev + 1)

5️⃣ State is immutable
👉 Use spread operator for objects/arrays

setUser({...user, city: "Mumbai"})
🔹 Example
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <>
      <h2>{count}</h2>
      <button onClick={() => setCount(count + 1)}>+</button>
    </>
  );
}
🔹 Types of State
Number → useState(0)
String → useState("")
Object → useState({})
Array → useState([])

👉 When state changes, the whole component re-renders
NOT just the part where state is used
👉 Only the component where state is defined re-renders
👉 AND all of its child components also re-render

❌ Parent does NOT re-render

--->note
“Q->If component re-renders, state should go back to initial value”
👉 But React does NOT reset state on re-render.
🔹 Why state is NOT reset?
When React re-renders a component:
It does NOT recreate the state

❌ Without prev
import { useState } from "react";
export default function Counter() {
  const [count, setCount] = useState(0);
  const handleClick = () => {
    setCount(count + 1);
    setCount(count + 1);
  };

  return (
    <>
      <h2>{count}</h2>
      <button onClick={handleClick}>Increase</button>
    </>
  );
}

👉 Click once → count = 1 (not 2) ❌

🔍 Reason:
React batches updates → both use same old count


✅ With prev
import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    setCount(prev => prev + 1);
    setCount(prev => prev + 1);
  };

  return (
    <>
      <h2>{count}</h2>
      <button onClick={handleClick}>Increase</button>
    </>
  );
}

👉 Click once → count = 2 ✅
❌ setCount(count + 1) → may give wrong result
✅ setCount(prev => prev + 1) → always correct
🧠 What is happening?

👉 React groups (batches) updates:

setCount(count + 1)  // both use same old value
React updates state after render, not immediately
👉 So inside same function → value is fixed (stale)
👉 But with prev:
prev = latest updated value each time
🧠 Simple Rule:
Situation	Use
Single update	setCount(count + 1)
Multiple / depends on old value	setCount(prev => prev + 1)

🔹 value vs without value in React (Paragraph Style)
In React, an input field can work in two different ways depending on whether you use
 the value attribute or not. When you use the value attribute, the input becomes a controlled component,
  meaning its value is fully controlled by React state. In this case, the displayed value always comes from 
  the state, and any change in the input must be handled using an onChange event. This approach is very useful 
  
  
  when you are working with forms, validations, or dynamic UI updates because React always has the latest value.

On the other hand, when you do not use the value attribute, the input behaves as an uncontrolled component. Here,
 the browser (DOM) manages the input value instead of React. This makes it simpler to use for basic cases, but
  React does not automatically know the current value unless you explicitly access it (for example, using refs). 
  While uncontrolled inputs are easier to set up, they are less powerful compared to controlled ones.

An important point to remember is that if you use the value attribute without an onChange handler, the input will 
become read-only, and the user will not be able to type anything. Therefore, controlled components require both 
value and onChange to work properly.
<input type="text" value={}>

--->⚛️ useEffect – 
🔹 Definition
useEffect is a React Hook used to handle side effects in functional components.
Side effects = API calls, DOM updates, timers, subscriptions, etc.
useEffect(() => {
  // side effect code

  return () => {
    // cleanup code (optional)
  }
}, [dependencies]);
🔹 Dependency Array Rules
[] → run once(used for API cals,initail setup)
[state] → run when state changes
No array → run every render
🔹 Important Points

✔ Runs after render (not during render)
✔ Can use multiple useEffect in one component
✔ Avoid infinite loops (wrong dependencies)
✔ Always include required dependencies
✔ Cleanup runs:

Before next effect
On unmount

-->Cleanup runs ONLY when the effect re-runs(dependency change) or component unmounts.
when dependency cahnge
useEffect(() => {
  console.log("Effect runs");

  return () => {
    console.log("Cleanup runs");
  };
}, [time]);

“Before running the new version of effect, clean the old side-effect first”

So it avoids:
duplicate intervals
duplicate listeners
memory leaks
when component unmount
🧠 FINAL SIMPLE RULE
👉 Cleanup runs in only 2 cases:
1. Before re-running effect
dependency changes → cleanup old effect first
2. Before removing component
component unmount → cleanup everything

useMemo executes its callback based on dependency changes and returns cached value

🔹 Why we need useMemo?

When a component re-renders:

All calculations run again ❌
Even heavy/expensive computations

👉 useMemo prevents unnecessary recalculations

🔹 Syntax
const memoizedValue = useMemo(() => {

  return result;

Function runs only when dependencies change
Otherwise, React returns cached value

import { useState } from "react";

👉 You are calling the function immediately

<button onClick={fun}>

👉 You are passing the function reference, not calling it

-->⚛️ Error Boundary in React
🔹 What is an Error Boundary?

An Error Boundary is a special React component that catches
 JavaScript errors in its child component tree and prevents 
 the whole app from crashing.

👉 Instead of crashing → it shows a fallback UI
🔹 Why we need Error Boundaries?
Without error boundary:
One error → 💥 Entire app crashes
With error boundary:

Error → ❌ Only that part fails
Rest of app → ✅ Works fine
🔹 Where Errors are Caught?

Error Boundaries catch errors in:
Rendering
Lifecycle methods
Constructors of child components

❌ They do NOT catch errors in:
Event handlers (onClick, etc.)
Async code (setTimeout, API calls)
Server-side rendering
Errors inside itself
🔹 How to Create Error Boundary
👉 Only Class Components can be Error Boundaries

✅ Basic Example
import React from "react";

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    // Update state → show fallback UI
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    console.log("Error:", error);
    console.log("Error Info:", errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return <h1>Something went wrong 🚨</h1>;
    }

    return this.props.children;
  }
}

export default ErrorBoundary;
🔹 How to Use It?

Wrap components with Error Boundary:

<ErrorBoundary>
  <MyComponent />
</ErrorBoundary>

👉 You can wrap:

Whole app
Specific components (recommended)
🔹 Example Scenario
function BuggyComponent() {
  throw new Error("Crash!");
}

<ErrorBoundary>
  <BuggyComponent />
</ErrorBoundary>

👉 Output:
Instead of crash → shows fallback UI


🔹 Lifecycle Methods Used
1. getDerivedStateFromError(error)
Runs when error occurs
Updates state
Used for fallback UI
2. componentDidCatch(error,errorInfo)
Used for logging errors
Sends error to monitoring services

| Thing       | Meaning                |
| ----------- | ---------------------- |
| `error`     | What went wrong ❌      |
| `errorInfo` | Where it went wrong 📍 |



⚛️ How Error Boundary knows an error happened?
React has an internal error handling system.
👉 When a child component throws an error during:
rendering
lifecycle methods
constructor

React automatically catches it and checks:

❓ “Is there any Error Boundary above this component?”

⚛️ How it handles the error?

React calls special lifecycle methods inside your class:

🔹 Step 1: getDerivedStateFromError()
static getDerivedStateFromError(error) {
  return { hasError: true };
}

👉 React calls this automatically
👉 You update state → hasError: true

🔹 Step 2: Re-render happens

Now this runs:

render() {
  if (this.state.hasError) {
    return <h1>Something went wrong 🚨</h1>;
  }
}

👉 Instead of broken UI → fallback UI shown

🔹 Step 3: componentDidCatch()
componentDidCatch(error, errorInfo) {
  console.log(error);
}
👉 Used for logging
👉 Runs after UI fallback

Note-->
If a component has these methods:

static getDerivedStateFromError()
componentDidCatch()
👉 React will treat it as an Error Boundary

this.state and useState do the same job, 
but they are used in different types of components
| Class Component | Functional Component |
| --------------- | -------------------- |
| `this.state`    | `useState()`         |

👉 Both are used to store and update data (state)

⚛️ Class Component (old way)
class Counter extends React.Component {
  state = { count: 0 };

  increase = () => {
    this.setState({ count: this.state.count + 1 });
  };

  render() {
    return <h1>{this.state.count}</h1>;
  }
}
⚛️ Functional Component (modern way)
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <h1 onClick={() => setCount(count + 1)}>
      {count}
    </h1>
  );
}
⚛️ Key Difference
🔹 this.state
Used in class components
Updated using this.setState()
🔹 useState
Used in functional components
Updated using setter function (setState)
⚛️ Important Truth 🔥

👉 Internally:

Both tell React → “data changed”
React → re-renders UI

notes->
👉 ✔ Return will update state ONLY inside this method:

static getDerivedStateFromError()
⚛️ Why return works here?
static getDerivedStateFromError(error) {
  return { hasError: true };
}

👉 React does this internally:

this.state = {
  ...this.state,
  hasError: true
};

👉 So return → updates state ✅

⚛️ But IMPORTANT ❗

👉 This works ONLY in this lifecycle method

⚛️ Normal case ❌
render() {
  return { count: 1 }; // ❌ WRONG
}

👉 This does NOT update state
👉 render() must return JSX only

⚛️ Normal state update way
this.setState({ count: 1 }); // ✅ correct
⚛️ So 3 cases
✅ Case 1 (Error Boundary)
getDerivedStateFromError() {
  return { hasError: true }; // updates state
}
❌ Case 2 (render)
return { count: 1 }; // not state update
✅ Case 3 (normal update)
this.setState({ count: 1 });
⚛️ Final Understanding

👉 ✔ Yes — return updates state
👉 ❗ BUT only inside getDerivedStateFromError()

⚛️ One-line (Interview 🔥)
Returning an object updates state only in specific lifecycle methods like getDerivedStateFromError,
 otherwise state is updated using setState().

function Users() {

  const {
    data,
    isLoading,
    isError,
    error
  } = useQuery({
    queryKey: ["users"],

    queryFn: async () => {
      const response = await fetch(
        "https://jsonplaceholder.typicode.com/users"
      );

      if (!response.ok) {
        throw new Error("Failed to fetch users");
      }

      return response.json();
    },
  });

  if (isLoading) return <h2>Loading...</h2>;

  if (isError) return <h2>{error.message}</h2>;

  return (
    <div>
      {data.map((user) => (
        <h3 key={user.id}>{user.name}</h3>
      ))}
    </div>
  );
}

export default Users;

function registerUser(e: any) {
  e.preventDefault();
  const formData = new FormData(e.currentTarget);
  const data = Object.fromEntries(formData.entries());
  console.log(data);
}
Suppose your form is:

<form onSubmit={registerUser}>
  <input name="name" />
  <input name="username" />
  <input name="password" />


  <select name="role">
    <option value="USER">User</option>
    <option value="ADMIN">Admin</option>
  </select>


  <button type="submit">Register</button>
</form>

User enters:

name     → Mohammad
username → naeem
password → 12345
role     → USER

Then:

const data = Object.fromEntries(formData.entries());

produces:
{
  name: "Mohammad",
  username: "naeem",
  password: "12345",
  role: "USER"
}

Each line
e.preventDefault();
→ Stops the browser's default form submission/page reload.

e.currentTarget
→ Gets the <form> that triggered the event.

new FormData(e.currentTarget)
→ Collects all form fields with a name.

formData.entries()
→ Gives the collected data as key-value pairs.

Object.fromEntries(...)
→ Converts those pairs into a normal JavaScript object.

Important

name is required:
<input name="username" />
id alone is not enough:

<input id="username" />  // ❌ FormData won't use this


target         → who triggered the event?
currentTarget  → where is the event handler attached?

Important difference: target vs currentTarget
Suppose:

<form onSubmit={registerUser}>
  <button type="submit">Register</button>
</form>

When you click the button:

e.target
   ↓
<button>

because the button caused the event.
But:

e.currentTarget
   ↓
<form>
